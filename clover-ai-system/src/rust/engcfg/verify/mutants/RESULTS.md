# Mutation check of the engcfg differential driver (independent verifier, 2026-10-25)

Question: can `verify/diff_driver` FAIL? I did not write the crate or the driver. Method: 140 mutant copies of the Rust crate (one change each, `mk_mutants.py`) plus an unmodified control (M00), each built with `cargo build --release --offline` in its own copy under `~/rustmig/engcfg/verify/work/mut/<name>/` on the box, and each run through the **unmodified** `verify/run.sh` (default settings: 4386 units, 24 jobs, `nice -n 10`, reference `ref/libengcfg_ref.so`), once as shipped (the driver stops scheduling new units after the first FAIL/CRASH) and once with `--keep-going` (every unit runs; counts of failing units per scenario). CAUGHT = at least one FAIL/CRASH unit in the as-shipped run. Crate sources, `ref/` and the driver were not changed (md5 before and after identical, `box-out/md5-before.txt` / `md5-after.txt`). No GPU, no CUDA call, no sudo; nothing under `~/k3gpu`, `~/ncm` or other agents' directories was touched.

Control M00 (byte-for-byte copy of `src/lib.rs`): PASS, 4386/4386 units, in the as-shipped and the `--keep-going` run, at the start and again at the end of the campaign (4 runs). Its `.so` md5 is `cb7a3cf1b605c1085347d2a45973c722`, the same as the md5 of the box's current `target/release/libengcfg.so`.

Which scenarios catch what (failing units under `--keep-going`; 123 caught mutants): E2+E7 32 (defaults, shifts, widths of settings, clamps, pend_cap), E5 28 (summary text), E6+E7 23 (selectors, prefill, trace, messages, exit status), E1+E2+E7 12 (atoi), E4 11 (force_routes), E3 7 (card_of), E5+E7 3, E2 3, E6 2, E4+E8 1, E3+E8 1.

The two weak spots the driver's author lists (`RESULTS.md` of the driver, "mutations a driver could easily miss"):

- **One-ulp float rewrites: all caught.** `100.0 * hc / need` as `hc / need * 100.0` (M106, M108) or `100.0 * (hh / need)` (M107); GB as `dr / 1e9 * raw` (M109) or `* 1e-9` (M110); `1000 * t / n` as `t / n * 1000` (M112), `1000 * (t / n)` (M113) or `t / (n / 1000)` (M115): each fails **100 of the 100 E5 units**. The probes count how often the rewritten expression differs from the original in the same run: M106 in 61,347 of 233,510 evaluations by value and in 3,650 by its printed `%.1f` text; M109 13,254 printed differences; M112 30,637 of 459,932 (`box-out/evcount.txt`). So the driver's near-tie generators do put the inputs of these quotients on rounding boundaries; "probably missed" was not borne out. Distinguishing inputs run by hand against both libraries (`box-out/hand-fp-pct.txt`, `hand-fp-ms.txt`, found by `fpsearch.cpp`): needed 80, hit_card 23 prints `28.8%` in the reference and the real library, `28.7%` in M106; n_calls 3, t_calls 0.0022499999999999998 prints `0.8 ms each`, M112 and M113 print `0.7`. The only ulp-looking mutant not caught, M114 (`t * 1000 / n`), is the same IEEE operation (multiplication is commutative): its `.so` is byte-identical to the real build.
- **Integer widths above 2^31: caught in settings, card_of and the messages, NOT caught in `force_routes`.** Caught: `reserve` and `host_bytes` in 32 bits (M18, M19), zero- instead of sign-extension (M20-M23), `pend_cap` in 32 bits / 128 bits / 3/5 (M47, M46, M48), call counts and `vq_cap` printed as 32 bits (M71, M72, M132), `card_of` product in 64 bits (M81). Not caught, all of them in `force_routes`: `total` in i32 (M98), `n * top` in i32 (M99), `fill` as u8 / u16 (M100, M101), the dealing counter in i32 (M102). The probes show the driver never reaches the distinguishing inputs (0 events for each, see below); each was constructed by hand and run against the reference, the real library and the mutant (`box-out/hand-u8-u16.txt`, `rest.txt`, `s32.txt`): the reference and the real library agree on every one of them, every mutant differs.

## NOT CAUGHT: verdicts and evidence

"Probed N times" = a copy of the mutant with one line added that appends a tag to a file whenever the changed path runs on an input where it could matter (`mk_probes.py`; the driver's workers append concurrently, so the tags were counted as substrings with `evcount.sh`), then the same full driver run (`run_probes.sh`, `--keep-going`, default seeds). The tags counted are in `box-out/evcount.txt`; the unit results of every probe are in `box-out/probe-summary.txt`. The counts belong to the driver's fixed seeds (`--seed0 1`).

### Equivalent (8)

- **M41, M42** (`acc >= 2^63` / `acc >= i64::MAX` in `strtol10`). Argument: at exactly 2^63 with a minus sign the original takes the `else` branch and returns `(2^63 as i64).wrapping_neg()` = `i64::MIN`; the mutant returns `i64::MIN` from the saturating branch. At exactly `i64::MAX` without a sign both return `i64::MAX`. Probes: the changed comparison ran on exactly -2^63 3,981 times (P41) and on exactly `i64::MAX` 3,986 times (P42) with 0 failing units. `cargo test --release` and `cargo test`: 56/56.
- **M43** (the digit loop stops at the first overflow). After `over` is set no later digit changes `acc` or `over`, `strtol10` returns only the value, and the end index is not used. Probe: digits were left after an overflow 55,029 times, 0 failing units; tests 56/56.
- **M82, M83** (`layer - 1`, `layer * cards` instead of the wrapping calls). The release profile has no overflow checks, so the compiler emits the same wrapping instructions: **the mutant `.so` is byte-identical to the real one (md5 `cb7a3cf1...`)**. The overflow occurred 9,453 (`layer - 1`, P82) and 542,307 (`layer * cards`, P83) times. Only the debug profile differs: plain `cargo test` fails `card_of_layout_1` (M82) and `card_of_layout_0` (M83) because debug builds panic on overflow; `cargo test --release` passes. So these two are equivalent for the shipped build and not if someone turns on `overflow-checks` for the release profile.
- **M103** (`top` zero-extended in the index). `top` is >= 1 in the contract ("top <= 0 is outside the contract"); for those values sign- and zero-extension agree. `top < 0` was never driven (0 events, P103). It would differ for negative `top`, which the driver does not test by design.
- **M104** (`fill[t]` zero-extended). `fill` starts at 0 and only grows; it is negative only after 2^31 deals to one token. 0 events (P104). Equivalent below 2^31 deals per token.
- **M114** (`t * 1000.0 / n` instead of `1000.0 * t / n`). IEEE multiplication is commutative; the `.so` is byte-identical to the real build (md5 `cb7a3cf1...`); the expression was evaluated 459,932 times (P114).

### Caught by a unit test only (2)

- **M84** (the explicit `abort()` before `d % cards` removed) and **M105** (the explicit `n < 0` abort removed): the driver passes (E8 sees SIGABRT in the mutant too: the Rust `%` by zero and `vec![0; n as usize]` with n = -1 both panic, and the shipped `.so` is built with `panic = "abort"`; paths reached 2 times (P84) and 1 time (P105), both in E8). `cargo test --release` and `cargo test` both fail `out_of_contract_inputs_abort_with_sigabrt` (exit status 101 instead of SIGABRT) because the test binary ignores `panic = "abort"` and unwinds. What the mutants change in the `.so` is the text on stderr at death (a Rust panic message), which E8 does not compare. For the shipped library these two are equivalent under the header ("the Rust library aborts"); the unit test is stricter than the driver, partly through a test-profile artefact.

## Driver weaknesses and proposed fixes (not applied)

1. **`force_routes` parameters stay small** (`n <= 200`, `top` in {1,2,3,4,8,16,17}, at most about 900 experts, compensated negative counts add at most about 60 deals): M98-M102 cannot be caught. Fix: a deterministic scenario E9 with the hand inputs above: `ntop32` (no memory), `u8` / `u16` (up to 280 KB), `total32` (about 260 MB, 16 s), and optionally the heavy `s32` (12.6 GB, about a minute, behind a flag and a memory check). `hand.cpp` shows the call sequence for each; every input is in contract (`top >= 1`, `n >= 0`).
2. **Counts longer than the experts are never generated** (M95). Fix: in `gen_fcall` add a mode that appends one to three counts (zeros, and a variant where a trailing negative count keeps the sum at n*top), and a mode with no experts and non-empty counts.
3. **The `fits` rejection is reached only through n = 0** (M92: 54 units of 4000). Fix: a mode that sets one count to n + 1 and lowers another by one so that the sum stays n*top (a count above n with the right total), for n >= 1.
4. **Write granularity is not observed** (M138) and the contract sentence "one write per original line" is not what the reference does for lines over 128 bytes. Fix: either drop the sentence from the header (the driver already compares bytes only), or capture fd 2 in the children through an `AF_UNIX`/`SOCK_DGRAM` socketpair (one write = one datagram) and require that each candidate datagram is a whole line ending in `\n` (the reference cannot be compared write for write because of the 128-byte split).
5. **E8 compares only the terminating signal** of the out-of-contract deaths. M84 and M105 differ in the stderr text of the death and are caught only by a unit test that relies on explicit `abort()` calls because the test profile unwinds. If the stderr text of a death matters, compare it in E8; if it does not, say so in the header.
