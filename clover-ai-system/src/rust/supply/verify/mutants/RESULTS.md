# Can the differential driver of the `supply` crate fail? Mutation check by an independent verifier

Date 2026-10-25, box `gpu` (`~/rustmig/supply`, user usergpu), local copy of the artefacts in `verify/mutants/` of the crate. I did not write the crate or the driver. **No GPU, no CUDA call, no sudo**; nothing of `~/k3gpu`, `~/ncm` or another agent's files or processes was touched or killed. Protected files are unchanged (md5 table at the end). Nothing committed or pushed.

## Answer

Yes. The driver (`verify/sy_driver`, 700 units per run, C++ reference against the Rust library, logs compared byte for byte) failed on **81 of 97 mutants**; the unmodified control **M00 passed 700/700** in three runs. It did **not** fail on 16 mutants:

| class | count | mutants |
|---|---|---|
| caught by driver | 81 | all others |
| caught by unit test only (`cargo test --release`) | 5 | M42, M43 (nchunk cap 7 / 9 instead of 8), M67 (fatal exit status 2), M74 (no exit when `check` returns), M93 (counter not reset by a second `sy_init`) |
| equivalent (argued, probed) | 8 | M16 (`vk` initial value), M26 (`break` -> `continue`, binary byte-identical to the control), M41 (`n_drive > pool_readers`), M57 (`pool_readers.max(1)`), M81 (`Relaxed` job counter, binary byte-identical to the control), M90 (NULL RAM cache in `host_worth`), M92 (NULL pool cache guard), M97 (`n == 0` with non-NULL list) |
| real gap, not caught by driver nor by unit tests | 3 | **M52** (file offset `e * raw` as a 32-bit multiply), **M62** (`got = r` instead of `got += r` in the pread loop), **M76** (one reader thread fewer than `min(readers, jobs)`) |

The three real gaps, and the weaknesses behind them, are in "Driver weaknesses" below with the proposed changes (not applied). M52 was shown to be a real failure: with the real record size the mutant dies where the original reads the right bytes (`demo/`).

## What was run

- **Mutants.** `mk_mutants.py` copies the crate to `~/rustmig/supply/verify/work/mut/<name>/` (Cargo.toml, Cargo.lock, src/, include/, slotcache-include/), applies exactly ONE textual change (the old text must occur exactly once) and builds with `cargo build --release`. M00 is an unmodified copy. 97 mutants: 93 in `src/ensure.rs`, 2 in `src/abi.rs` (M94, M95), 2 in `src/lib.rs` (M96, M97). Diff of each: `<name>.diff` (first line = description). Classes: first sync / vq, prot construction, card hit order and counters, victims, host take-out order, held slots, write-back conditions and counters, event record, prefill sources, chunk arithmetic (cap 8, ceil, 4096 rounding, `>=`, `len`), job offsets, reader count (`min`), pread loop (short reads, `r <= 0`, error text, exit status), `check`, thread numbering / spawning / job order / counter, end-of-call order and timers, `ekey`, NULL-cache guards, ABI field order, `sy_wb_skipped`, `sy_init` reset.
- **Driver run.** `run_all.sh`: `RUST=<mutant .so> JOBS=24 ./run.sh mut/<name> --keep-going`, the driver's default full run (Y1-Y9 60/60/60/60/80/60/60/60/60 units, YF 80, T1 60 = 700), one run at a time, `nice -n 10`, own private terminals, shared data directory (the files the drive reads come from are a pure function of scenario and seed). CAUGHT = at least one `UNIT <scn> <seed> FAIL` line in `units.log`. Counted by `analyze.py` and again independently by `count_check.sh` (grep): 98 runs, 68,600 UNIT lines, 700 per run, no duplicate, 31,227 FAIL lines, 81 runs with at least one FAIL, 17 with none (M00 + the 16).
- **Raw evidence read by me** (not only script output): the `.res` and `.diff` of the first failing unit of M13, M36, M45, M63, M64, M80, M91; `units.log` of every run; the probe event files (head and counts); `test-<name>.txt` of every uncaught mutant; the driver source (`do_unit`, the atexit handler, the thread statistic).
- **Repeats.** The control and the 16 uncaught mutants were run two more times each (`rerun.sh`): 700 units, 0 failing, every time (`logs/reruns.txt`). The caught ones are not flaky in a way that matters: the lowest counts (M63 2 units, M45 6, M91 10) were read unit by unit above and each has a real first difference.
- **Unit tests.** `cargo test --release` in every uncaught mutant and the control (`run_tests.sh`, `logs/tests.txt`): M00 25/25 pass.
- **Probes** (`mk_probes.py`, `run_probes.sh`, `probe_summary.sh`): for each uncaught mutant a build with the mutation plus lines that append `<pid> <tag>` to a file whenever the changed path runs; a full driver run of each (all 15 probe builds passed 700/700). Results in the verdict section and `logs/probe-summary.txt`.
- **Disk.** Free space on `/` stayed at 104-106 GB (95 % used by other users) during the whole job; my out dirs peaked at 549 MB (raw per-unit logs are deleted after every run: `u<seed>.*.log`, `.log.gz`, `.trace`, `.try1`, `.il`, `.cov`; units.log, summary.txt, `.res`, `.diff` kept until the end). At the end `verify/out/mut` and `verify/work` were deleted; `verify/mutants/` is 20 MB. Free space was checked before every run (`run_all.sh` stops below 40 GB) and every 5 mutants.

## The uncaught mutants: evidence

Probe = the mutant plus a line appended to a file whenever the changed path runs; each probe build was run over the full driver set and passed 700/700 (`logs/probes.txt`, `logs/probe-summary.txt`; event files stay on the box only until cleanup, the counts are here). "Processes" = distinct child processes that wrote at least one event.

**Equivalent (8)**
- **M16** `vk` initial 0 instead of -1. `slotcache.h` (sc_acquire): "else `*vkey = -1`", written in every case. P16 (sentinel -2): after every `sc_acquire` of 93,819 calls in 717 processes `*vkey` had been written (victim key 90,250, -1 3,569, untouched 0). Unit tests 25/25 pass too (a fake that does not write `*vkey` would show it; none exists).
- **M26** `continue` instead of `break` when the RAM cache has no capacity or prefill is on: the condition does not depend on the victim, so the next iteration does the same test. The mutant's `.so` is **byte-identical** to the control (md5 b0288adb...), i.e. the compiler removed the difference. P26: the changed path ran 15,780 times in 116 processes (15,241 with more than one victim).
- **M41** `n_drive > pool_readers`: for `n_drive == pool_readers > 0` the other branch gives `min(8, (2n-1)/n) = 1`, the same nchunk. P41: reached 1,124 times in 344 processes, the other branch would give 1 every time.
- **M57** `pool_readers.max(1)`: nchunk is 1 for `pool_readers <= 1` with or without the clamp, and `run_parallel` spawns nothing for `n <= 1`. P57: reached 248 times in 57 processes (196 with jobs to run).
- **M81** `Ordering::Relaxed` on the job counter: `.so` byte-identical to the control (x86-64 `lock xadd` for both orderings). Equivalence is for this target only; the author's note 7 ("invisible") holds.
- **M90** NULL RAM cache not worth a slot: needs `host_worth` with a NULL cache; the contract allows a NULL RAM cache only with `cap_slots == 0` or prefill, where the write-back loop leaves before asking. P90: 74,420 calls of `host_worth` in 562 processes, 0 with a NULL cache.
- **M92** no NULL guard in `pool_find`: a NULL pool cache is outside the contract. P92: 182,487 calls, 0 with NULL. Equivalent only because that input is out of contract; nothing (driver or unit test) checks the behaviour NOTES.md describes for it.
- **M97** `n == 0` with a non-NULL list: `from_raw_parts(p, 0)` is an empty slice like `&[]`. P97: 19,479 calls in 759 processes, none with `n == 0`.

**Caught by unit test only (5):** M42 and M43 (`chunking_table_derived_by_hand`: real record 17547264: (8, 2195456) expected), M67 and M74 (`fatal_paths_message_status_and_the_calls_before_them`), M93 (5 tests; the shared global makes four fail as a side effect). All pass in the control (25/25).

**Real gaps (3), not caught by the driver or by any of the 25 unit tests**
- **M52** `off = (e as i32 * raw as i32) as i64`. P52: 85,409 jobs in 671 processes; the 32-bit product equalled the 64-bit one in every one (largest `e * raw` of any job: 3,665,920; 2^31 = 2,147,483,648), because all records are 4-20 KB. `demo/m52_real_size.c` (fake ops, a sparse file of 896 real-size records, 15.7 GB apparent): control reads the right bytes for e = 5, 100, 200, 895; M52 right for 5 and 100 and **`reading expert 200 of layer 0 failed: Invalid argument` / `expert 895 ... Invalid argument` (exit 1)** (the offset wraps negative). So the mutant is a real bug at the engine's size and invisible at the driver's.
- **M62** `got = r`. Only a successful short read followed by another read makes it differ. P62: 2 short reads in 700 units, both at the end of the cut file (the next `pread` returned 0 = fatal); 0 loop iterations with `got > 0` and `r > 0`. Regular files do not give short reads in the driver's sizes.
- **M76** `for i in 1..(n-1).max(1)`: n-2 threads are spawned (0 when n = 2) instead of n-1. P76: 12,098 `run_parallel` calls in 671 processes, 9,598 with `n >= 2` and 6,562 with `n >= 3`, where the mutant runs on fewer threads than the original. The driver's thread check only asks that more than one thread took jobs in half of the calls with at least 8 jobs (`g_multi_k * 2 < g_big`).

## Driver weaknesses and proposed changes (nothing applied)

- **W1 exit status value (M67).** `at_exit_flush` (sy_driver.cpp:210-215, registered at :644) ends every child with `_exit(g_exit_code)`, `g_exit_code = 1` while running, whatever the status the library passed to `exit()`. So a library that exits with 2, 0 or 255 where the original exits with 1 is indistinguishable (M67 passed all 47 fatal-path units, P67). `verify/RESULTS.md` says the exit status is part of the comparison; only "exit() was called" is. *Proposal:* register the handler with glibc `on_exit(fn(int status, void*), ...)`, write `EXIT <status>` into the log (and make the parent's status check use it).
- **W2 record size (M52, M42, M43).** Every record is 4-20 KB. (a) `e * raw` never exceeds 2^31 (P52), so a 32-bit offset bug is invisible; (b) `chunk` is the same 4096 for every `nchunk >= 5` below 20 KB, so the cap 8 cannot be seen (P42 and P43: 941 calls with ratio >= 8 in 217 processes, 480 with ratio >= 9, chunk sizes for 7 / 8 / 9 chunks equal every time). *Proposal:* a scenario (say Y10, a few units) with `raw` in {65536, 4 MiB + 4097, 17547264}, E = 896 and experts drawn above `2^31 / raw`, on sparse files (`ftruncate`) whose bytes are the same pure function but non-zero only in the first and last 64 bytes of each record (the existing byte-hash checks then work on mostly zero records; the cost is hashing a few hundred MB per unit). For the cap, `raw = 4 MiB + 4097` with one expert and 8 or more readers gives three different chunk sizes for 8 / 7 / 9 chunks (528384 / 602112 / 466944, computed by hand from the formula in `supply.h`), so min(7), min(8), min(9) differ; `raw = 65536` would not separate 8 from 9 (both 8192). `demo/m52_real_size.c` shows the offset case in isolation.
- **W3 thread count (M76).** `dk.size() >= 2` in half of the big calls does not pin the number of threads. *Proposal:* in T1 make the fake `set_device` of a reader job wait (bounded, e.g. 200 ms) until `min(pool_readers, njobs)` distinct thread numbers have arrived, then log the number that arrived; with jobs >= threads every thread must take one job before any finishes, so the count is deterministic and must equal `min(pool_readers, njobs)`. A supply with one thread fewer would time out the barrier with one thread missing, visible in the log.
- **W4 short reads (M62).** The driver cannot make a successful short read. *Proposal:* a scenario in which the driver executable itself defines `pread` (the dynamic symbol of the executable is found before libc's by both arms), returning a seeded shorter count (1 byte up to len) for each call; the original's loop must give identical logs, and a unit where the interposer ends in a real EOF after a short read keeps the fatal path.
- **W5 `check` that returns (M74).** The fake `check` never returns on a non-zero status, so the line after it in `do_check` cannot run in the driver; only the unit test covers it. *Proposal:* a YF variant whose `check` returns with the status; both arms must stop at once with exit 1 and no further ops call.
- **W6 out-of-contract NULL pool cache (M92) and `n = 0`**: not driven; fine under the contract, but nothing pins the documented behaviour either.
- **Author's list of easy-to-miss mutations (verify/RESULTS.md) checked against this run.** 1 (thread order / thread count): confirmed for the count (M76), the order is caught with one thread (M79 caught in 309 units). 2 (`prot` order): untested here beyond M05 (no sort; caught only through non-adjacent duplicates); a pure reordering was not mutated. 3 (`t_*` values): **refuted**, M85-M88 are caught. 4 (`dk` / `dh`, `vk` init): confirmed invisible, and equivalent (M16). 5 (failure injection, 1st-3rd occurrence, one thread): not mutated here. 6 (`sy_init` twice, `n = 0`, first-call check): `sy_init` twice is unit-only (M93), `n = 0` equivalent (M97). 7 (memory ordering, clock): confirmed (M81 byte-identical). 8 (chunk model shared by the author): caught the mutations I tried (M40-M51) except the cap (W2). 9 (`pend_take` / `arr_wait` modelled as completing at once): not mutated.

## Not covered by this exercise

Mutations of the reference arm, of the driver, of the slot cache; the other ten check-site texts (only one was mutated, M73); the declared order of fields inside `sy_ops` / `sy_pool`; the busy flag; panic / abort behaviour of `Ctx` under real races; memory-safety tools (no ASan, Miri, TSan, loom). Mutants are single-site; no combination of two bugs was tried. All numbers are for this box (x86-64, rustc 1.95.0, one set of seeds per scenario, the driver's default counts).

First pass of all 98 runs: `run_all.sh` deleted raw logs with `find ... -name '*.log'`, which also deleted `units.log`; the verdict counts could be rebuilt from `.res` files but the pass was repeated in full with the narrower pattern `u[0-9]*.log` (the table is from the second pass; `logs/progress-pass1-units.log-deleted.txt` is the first pass's progress file).
2. First version of `run_tests.sh` printed the last `test result` line (the empty doc-test run). Regenerated from the logs with `head -1` (the first version's file is kept as `logs/tests-first-version-last-result-line.txt`).
3. First version of the probe writer used `writeln!` (several `write` calls), so concurrent children interleaved their lines; probes were rebuilt with one `write_all` per line and re-run. The totals of events were identical in both runs; only the process counts of the first run were wrong (`logs/probes-first-version-interleaved-lines.txt`).
4. 94 stray files (75 empty, 19 holding twelve counters such as `0 0 0 ...`) appeared in `~/rustmig/supply/verify/` between 03:03 and 03:17 UTC with random binary names. They are the driver child's coverage file (`<log>.cov`): the child opens its path at exit, and a mutant that corrupts the child's heap (an overflowing `len` such as M50 is the likely one; not diagnosed mutant by mutant) overwrote the path string. They were created by my runs only (times match, none after 03:17, none from the probe or repeat runs) and were deleted by `finalize.sh` (`find . -maxdepth 1 -type f -newer mutants/mk_mutants.py`).
5. The shared `run_in_terminal` sync terminal showed another agent's command and swallowed mine again; all long commands ran in private async terminals with output redirected to files.
6. Nothing was killed. Processes of other agents (for example their own `./run_all.sh`) were present on the box during the work and were left alone.
