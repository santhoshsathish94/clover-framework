# Differential driver of poolinit against mutants (independent verifier, 2026-10-25)

Question: can the differential driver of the Rust crate `poolinit` (`verify/pi_driver.cpp`, C++ reference `ref/libpoolinit_ref.so` against `libpoolinit.so`, logs compared byte for byte plus an in-driver model of decode.cuh@4d8d891) FAIL?

**Answer: yes, and it does so for 102 of 122 deliberately broken copies; 20 pass (60,000 units each, 0 failures). Of those 20 only 7 are real behaviour changes the driver cannot see (5 of them about the "seconds" field and the calling thread, 2 about the order of the registered chunk addresses); the rest are equivalent, outside the contract, or caught by `cargo test` only.** Nothing here was run on a GPU or against a CUDA call. Written by an independent verifier; the crate sources and the driver were not changed.

## What was run

- Mutant = scratch copy of the crate in `~/rustmig/poolinit/verify/work/mut/<name>/` (Cargo.toml, Cargo.lock, src/, include/, slotcache-include/), exactly one logical change in `src/*.rs` (some changes need two or three textual edits, e.g. M33, M42, M80), built with `cargo build --release`. 122 mutants M01-M122 plus M00 (unmodified copy, control). Diffs: `M*.diff` here (first line = description). Mutant list and md5 of each `.so`: `md5list.txt`; generator: `mk_mutants.py`.
- Driver run per mutant: `RUST=<mutant .so> ./run.sh mut/<name> --keep-raw 0 --keep-going` with the default counts H 600, HX 400, P 600, PX 800, PR 200, M 400 = **3,000 units**, one run at a time, `nice -n 10` (`run_all.sh`). CAUGHT = at least one `UNIT ... FAIL` line in `units.log` (`analyze.py` counts them; the shell recounts `grep -c '^UNIT'` / `PASS` / `FAIL` into `progress-3000.txt`: every run has exactly 3,000 UNIT lines, no duplicates). First failure = lowest seed of the first scenario (order H HX P PX PR M) with a failure; the two differing lines come from that unit's `.diff` or the `VIOLATION` line of the Rust log. The raw logs of that first failing unit are kept in `logs/<name>/` (all others were deleted after each run, as ordered).
- **Control M00** (built in a fresh directory): md5 `b5cba5c42004363fdb7f718a112407e8`, identical to the `.so` that sits in `~/rustmig/poolinit/target/release/` on the box; 3000/3000 PASS, the per-scenario event-line counts are the author's `final-1` numbers (H 7006, HX 858, P 16467, PX 12618, PR 6252, M 15088). I read the raw logs of a separate control run (seeds 1-3 of each scenario kept; H 1, HX 1, PR 1 read in full): a 3-chunk host call prints `K3GPU: host expert cache of 96 slots (0.0 GB) pinned in 0.0 s`, the HX unit prints `host expert cache: cannot map 1966080 bytes` and ends with `EXIT_IN_LIBRARY ok`; ref and Rust logs are equal.
- Each mutant that the 3,000-unit run did not catch (20): (a) **60,000-unit run** (20 times the counts, `run_big.sh`): all 20 had 60000 UNIT / 60000 PASS / 0 FAIL / 60000 distinct (scenario, seed) pairs (`progress-big.txt`; the `.res` files of these runs were deleted after the recount to keep the disk use down, `units.log` and `summary.txt` stayed on the box); (b) `cargo test --release` inside the scratch copy (`run_ctest.sh`, `ctest/<name>.txt`); (c) for the ones that needed it, a **probe build** = the same mutant plus a line appended to the file named by `PI_PROBE` whenever the changed path runs (`mk_probes.py`, `run_probes.sh`, `probe_count.py`, `probe-summary.txt`); every probe build passed 3000/3000 itself, so the probe does not change what the driver sees.

## The 20 mutants that were not caught: evidence

**M03 (the calling thread does not map; 15 helpers do all the work).** The header says 16 workers, "also works on the chunks itself". Driver: the number of `pthread_create` calls (15) is checked, not who maps. 0 failing units of 3000 and of 60000; `cargo test` 13/13 pass. Not equivalent to the header text, but also not observable per unit in the original: probe `M00c` (original + "which thread mapped this chunk"), 3000 units, 1062 host processes: the calling thread mapped at least one chunk in **111 of 737 processes with >= 8 chunks (15%)**, in 30 of 105 with exactly 16 chunks, in 0 of the 91 with 1-2 chunks; helpers are simply faster than the caller. A check "the caller mapped something" would fail on the original. Probe `M03p`: the mutated path ran in 1285 processes. Fix proposal and prototype below.

**M11, M12, M13 (seconds of the summary line measured after the mapping / in milliseconds / constant 0.0), M14 (CLOCK_REALTIME instead of CLOCK_MONOTONIC).** The driver masks the number and checks only its shape `%.1f`. Raw check (`rawchk.sh`, host seeds 1-11, ref and Rust stderr side by side, all 11 units PASS for every mutant): the original prints `pinned in 0.0 s` every time; M12 prints `pinned in 2.7 s`, `3.8 s`, `2.5 s`, `1.0 s`, ... (even `0.8 s` for the unit with 0 chunks) next to the original's `0.0 s` and the unit passes. Probes `M11p`-`M14p` (975 host processes each): the original's true elapsed seconds had min 0.0004, median 0.002, max 0.0416 (M11p run; the M12p and M13p runs have max 0.0376 and 0.0318) - **always below 0.05, so the printed value is always "0.0"**; M11 and M13 print 0.0 as well (mutant seconds 0 in all), M12 prints median 1.85 and up to 37.6 seconds and still has the shape `%.1f`; M14: elapsed on CLOCK_REALTIME equals elapsed on CLOCK_MONOTONIC to the microsecond (`d_real == d_mono` min/median/max 0.000442 / 0.0018835 / 0.035664). `cargo test`: 13/13 pass for each of M11-M14. M15 (nanoseconds scaled 1e-6) is caught in 7 units only because a unit that straddles a second boundary prints `-955.6 s`.

**M33 and M46 (the order in which the chunk addresses are registered / handed out is reversed, either both loops or the table index).** Under the header the chunk number is the value taken from the shared counter, and which address a chunk number gets is free, so no single unit can show the change (0 failing units of 3000 and 60000; `cargo test` pass). But the order is **measurable statistically**: probes `M00r`, `M33r`, `M46r` log the address of every chunk in the order of the `host_register` calls (3000 units each, 724 processes with >= 4 chunks, the three runs have the same configuration): original - registered addresses descending in 399, ascending in **4**, neither in 321; M33 - ascending in **368**, neither 356, descending 0; M46 - ascending in **367**, neither 357, descending 0 (Linux hands out descending addresses to successive `mmap` calls, threads race a little). A pooled check over the units ("ascending in less than 2% of the multi-chunk units") would kill both; it tests the kernel's placement and the claim order, not a sentence of the header, so I list it as a real gap of the driver but not as a defect of the contract.

**M57 (error_string called twice), M58 (the `file:line: ` prefix and the text written with two `write()` calls).** Executed in 583 passing processes each (probes `M57p`, `M58p`). The fake `error_string` is a pure function and does not count calls; stderr is a file, so one or two `write()` calls give the same bytes. Nothing in the header fixes either. `cargo test` passes. Driver-blind; the original's `CHECK` evaluates `cudaGetErrorString(e)` once and prints with one `fprintf`.

**M47 (all atomics Relaxed).** The chunk table is read only after `std::thread::scope` has joined every helper (join is a synchronises-with edge), the counter only needs atomicity. Equivalent. Probe `M47p`: 12836 stores executed, all units passed; 60000 units passed.

**M48 (final cap = `cap0 & !31`), M49 (`chunk_bytes = raw << 5`).** `n_chunks = cap0 / 32` so `n_chunks * 32 == cap0 & !31` for every `usize`; `x << 5 == x * 32 (mod 2^64)` and the original multiplies with wrapping. Equivalent by arithmetic; probes: `M48p` 1092 calls, `equal=true` 1092, `false` 0; `M49p` 1517 calls, `equal=true` 1517 (raw from 2048 to 17547264), `false` 0.

**M59 (`exit1()` via `std::process::exit(1)`).** Rust's `exit` calls `rt::cleanup()` and then libc `exit(1)`, so atexit handlers run and the status is 1. Probe `M59p`: executed in 1428 passing processes; the driver's `atexit` handler checks the out struct at every one of them. Equivalent.

**M67 (`free >= reserve`), M68 (`saturating_sub`).** Both give `usable = 0` when `free <= reserve`, as the original. Probe `M67p`: 1998 calls, `free == reserve` in 61, `free < reserve` in 101; `M68p`: 101 calls with `free < reserve`; all units passed. Equivalent.

**M86 (`experts as u32 as usize` instead of the sign-extending cast).** Differs only for negative `experts`, which the header lists as not handled (`experts < 0`). Probe `M86p`: 1074 pool calls, `experts < 0` in **0**; the driver draws `experts` from {0, 1, 17, 896, 4096}. Outside the contract domain; I record it because the driver would not see it even if the contract were extended.

**M117 (`pi_expert_stats` field order changed).** The resulting `libpoolinit.so` has the md5 of M00 (`b5cba5c4...`): nothing reads or writes `st`, so the compiled code is byte for byte the same; no test of the binary can tell the two apart. `cargo test` fails in `struct_layout_equals_the_c_header` (it compares the offsets of every field with a C compile of the header): a source-level check, as intended.

**M120, M121, M122 (argument checks of `pi_pool_init`: no `expert_raw == 0` check; no `host_alloc` NULL check; other message text).** The driver never passes NULL pointers or `expert_raw == 0` (the header calls these additions of the library). `cargo test` fails in `null_arguments_and_zero_expert_raw_are_refused_first` for all three (M120 shows `attempt to divide by zero ... panic in a function that cannot unwind`).

## Weak catches of the driver (<= 30 failing units of 3,000)

- **M09 / M10** (GB divisor 2^30 / GB floored): 11 units. The GB figure is printed with one decimal and the driver maps at most 48 MiB, so it reads `0.0` except for the units with exactly 48 MiB (0.0503 GB prints `0.1`): the digit is only checked in the 11 units that failed (H 8, M 3). The real engine prints 160.6 GB; that path is only in the unit test `host_plan_and_summary_with_real_constants`.
- **M15** 7 units (see above), **M54** (NULL `error_string` prints '' instead of '(null)') 28 units (`null_err` is drawn at 4%), **M102 M103 M105 M106 M107** (CHECK line numbers of event / d_eptr malloc / slab malloc / copy stream / pool set_device) 13 / 15 / 15 / 13 / 27 units: a failure has to be injected at exactly that call, and the injection position is drawn at random per unit. All were caught within 3,000 units, the 60,000-unit counts were not run for caught mutants.

## Driver weaknesses and proposed fixes (none applied)

1. **The seconds field (M11-M15).** Only its shape is checked and, as measured, it is always `0.0`. Proposal (prototyped in a scratch copy, `proto_driver.py` + `proto_run.sh`, not applied to `pi_driver.cpp`): in host steps make every interposed `mmap` sleep 60 ms; require the printed seconds to lie in `[round1(ceil(n_chunks / 16) * 0.060), wall time of the call + 0.06]`; interpose `clock_gettime` so that each `CLOCK_REALTIME` reading is shifted by +1000 s per reading while `CLOCK_MONOTONIC` is real. Result (3,000 units each, `phase4.log`): control M00 **0 failing units** (no false alarm), M11 740, M12 975, M13 740, M14 975, M15 975 failing units; every host unit with at least one chunk fails for M11/M13, the others fail on every host unit including the 0-chunk ones. First lines: `PROTO: reported 0.0 s outside [0.099, 0.180] (n_chunks 17, wall of the call 0.120)` (M11, M13), `reported 0.6 s outside [-0.001, 0.061] (n_chunks 0, ...)` (M12), `reported 1000.0 s outside ...` (M14).
2. **Participation of the calling thread (M03).** Same prototype: with 60 ms sleeps in `mmap` and `n_chunks >= 16`, all 16 workers get a first chunk, so the calling thread must have called `mmap` at least once (recorded by `gettid` in the interposed `mmap`). Result: M03 **248 failing units**, control 0 of 3000 (`PROTO: n_chunks 17 >= 16 with 60 ms mmaps but the calling thread never called mmap`). The run time of a driver run grows (about 1,800 host units x ~0.1 s).
3. **Registration order (M33, M46).** Pool the registered-address order over the units (ascending in < 2% of the units with >= 4 chunks) or, better, decide whether the header should say that chunk number order is address order; as it stands this is a kernel / race property. Not prototyped.
4. **GB digit (M09, M10).** The 48 MiB cap hides the digit. Mapping 1-4 GiB chunks per unit costs memory unless the interposed `mmap` returns a `MAP_SHARED` alias of a small memfd (the library's zeroing would then touch the same pages); not tried. The pure function is covered by a unit test.
5. **`error_string` call count and the number of `write()` calls (M57, M58).** Count the calls (one per failed CHECK, none otherwise) and interpose `write` on fd 2; cheap, not prototyped. Low significance.
6. **Unbounded event recorder.** `X.events` and `g_acc[]` keep one entry per `sc_add_spare` call, so a library that returns an absurd slot count makes the driver allocate without limit (see Hazards). Proposal: abort the unit as FAIL when the recorded events exceed a bound (e.g. 1,000,000). 
7. **Crash handler.** Every aborting child starts `apport` (about 8 s per crash in my runs); `prctl(PR_SET_DUMPABLE, 0)` in the child would avoid it (I used an `LD_PRELOAD` shim, `nodump.c`).

## Hazards met while running (and what I did)

- **Memory.** First attempt of M69 and M70 had no memory cap: the driver's event recorder grew to 8-14.5 GB resident in each of dozens of children (a mutant that makes `slots` huge produces up to 2^31 `add_spare` events, 56 bytes each plus the real-cache vector). Box free memory was about 100 GB (of 376) at the lowest I saw; the 63-67 GB resident `k3_chat_server.py` of another agent was untouched and still running at my last look. I killed my processes by hand (matching only `pi_driver` processes whose cwd is `~/rustmig/poolinit/verify`, after an early `pkill` whose pattern did not match the `./pi_driver run` parent had let new units start), deleted the partial outputs, and re-ran M69 / M70 and everything after with `ulimit -v 3000000` and `JOBS=8`. This broke the order "real memory used by a unit must stay small" for about two minutes and is mine to own; the cap keeps it below 3 GB per process from M69 on (M01-M68 ran without the cap; I did not log their memory use, each run took 3-10 s). `progress-3000.txt` and `analysis-3000.log` still contain the lines of the aborted first attempts of M69, M70 and M90 (the later lines of the same names are the valid runs; `results-3000.tsv` has one row per mutant).
- **Crash handler.** M90's first attempt crawled because every aborting child waited for `apport`; I restarted M90-M122 with the `LD_PRELOAD=nodump.so` shim (`PR_SET_DUMPABLE 0`). The signal is still delivered (units show `sig6` / `sig11`), nothing else changes.
- **Probe file.** The first version of the probe wrote one line with several `write()` calls and the lines of concurrent processes interleaved; the first probe runs were discarded, the probes rebuilt with one `write()` per line and re-run (the numbers in this file are from the second run).
- **Documentation.** `NOTES.md` / `verify/RESULTS.md` of the crate quote `libpoolinit.so` md5 `c40ad1bf36e39bd77fd4f3566fb6ad69`; the shipped `.so` on the box and a fresh build of the unmodified sources (M00) both have md5 `b5cba5c42004363fdb7f718a112407e8`. The md5 of the source files in NOTES.md match the box, so the library was rebuilt (different toolchain output) after the note was written; I did not look for the reason. (`NOTES.md` and `verify/RESULTS.md` have a modification time during my session, 07:49 local; I did not touch them, and they still quote `c40ad1bf`.)
- **Disk.** Free space on `/` at the start 106 GB, lowest 103 GB, at the end 106 GB (never near the 40 GB stop level). My own output was at most 2.1 GB in `out/` (`out/mut` 1.7 GB, `out/probe` 244 MB, the rest 60,000-unit logs and control runs) plus 141 MB in `work/` just before the final cleanup, so under the 3 GB limit; after the cleanup `work` is 15 MB and `mutants` 3.8 MB.

## Not covered

- No GPU, no CUDA call; no real mapping above 48 MiB (every number above is about the driver's units, not the engine with 561 MB chunks).
- 102 caught mutants were run once at 3,000 units (the run is deterministic apart from thread timing: M42 "threads not joined" fails in 516 units because it is a race; I did not repeat it to see the spread).
- Mutants of the reference `poolinit_ref.cpp`, of the driver's model, and of `tests.rs` were not made. Only the Rust crate (host.rs, pool.rs, sys.rs, abi.rs, lib.rs) was mutated; `Cargo.toml` flags (`panic = "abort"`, opt level) were not.
- The classification "equivalent" for M47 M48 M49 M59 M67 M68 rests on the arguments above plus the probes showing the path ran (and for M48/M49 that the two expressions never differed); it is not a proof for M47 and M59 (memory-model / std internals).
- `cargo test` was run only on the 20 not-caught mutants.
