# poolinit differential driver - results (2026-10-25, box `gpu`, no GPU, nothing CUDA executed)

Question: do the C++ reference (`ref/libpoolinit_ref.so`, the original text of `HostCache::init` / `CardPool::init` behind a harness) and the Rust library (`target/release/libpoolinit.so`) leave the same traces behind when the same seeded call is made against both? And do both agree with a model of decode.cuh@4d8d891 written inside the driver? This is a first driver; the mutation controls and the independent review are for other agents.

Files: `pi_driver.cpp` (modes `child`, `unit`, `run`, `cfg`), `build.sh`, `run.sh`, `final.sh` (rebuild everything and run), `coverage.py` (what the units contain). Libraries under test: `libpoolinit_ref.so` md5 `070e70c16e120a0e7613afde8169d102`, `libpoolinit.so` md5 `c40ad1bf36e39bd77fd4f3566fb6ad69` (`cargo build --release` at the end of the work; the same md5 in every run below). Real slot caches: `~/rustmig/slotcache/target/release/libslotcache.so` (used by both arms).

## What a unit is

One seed of one scenario = a list of 1..3 init calls (`pi_host_init` / `pi_pool_init`) run in a child process per library (ref and Rust in parallel), logs compared byte for byte, exit statuses compared. Scenarios: **H** host cache (1 call); **HX** host cache with a failing op (set_device, a register) or a failing mmap; **P** card pool; **PX** pool boundaries (62, 63, 64, 65 slots; slot counts that wrap in the cast to int; free below the reserve) and a failing op at a random position; **PR** the engine's real constants (EXPERT_RAW 17547264, EXPERTS 896, reserve 2500 MiB, 24 GiB total; fake ops only, nothing mapped) plus a host call with fewer than 32 experts of budget; **M** two or three calls in one process (host and pool, caches shared between calls).

What is real and what is fake inside a child:
- **Real:** `mmap`, `madvise(MADV_HUGEPAGE)`, the zeroing, the 15 helper threads (the driver executable is linked `-rdynamic` and defines `mmap`, `madvise` and `pthread_create`, which both libraries reach through the dynamic linker; when armed they record every call, can make the k-th mmap fail, and in poison mode fill each new mapping with 0xA5 so the library's zeroing is observable). `libslotcache.so` receives the spares (in 3 of 4 steps; in the others a recording stub with arbitrary cache pointers, NULL included, takes them).
- **Fake:** the CUDA ops (`pi_ops`): recorded, with addresses from fake arenas (seeded start), handles counting up by 16, memory info configured per unit, a failure with a configured code at the k-th CUDA call, `error_string` returning `E<code> <text>` (text with `%s %d %n` and a non-ASCII byte in half of the units) or NULL (4%).
- **Sizes:** a host step maps at most 48 MiB (`expert_raw` from 2048 to 131072, chunks of 64 KiB to 4 MiB, 0 to 24 chunks); the card pool maps nothing. Real constants are used only in PR, through the recorded call arguments.

What is compared (the child writes it into the log, the parent compares the two logs): the ordered list of ops calls with their arguments and results (spares as runs of consecutive slot numbers, normalised to chunk / slot or slab slot numbers and a cache identity); for the register calls the page alignment, non-overlap and (poison mode) all-zero content at the time of the call; the number and arguments of mmap calls (length, prot, flags, fd, offset), of madvise calls (address = a mapped region, length, `MADV_HUGEPAGE`, and in poison mode the region still poisoned when madvise is called, i.e. zeroed after it), of `pthread_create` calls (15, also for 0 chunks), that all of them precede the first op, that the registered regions equal the mapped ones and are distinct, that every page is resident (mincore, no-poison mode) or zero (poison mode); the out struct after the call (and, on fatal exits, as seen by an `atexit` handler) including the entries and `st` that must not be touched; the whole stderr text of each step with the seconds masked (the number is checked to have the shape `%.1f`); the exit status; the real cache's spare vector (`sc_snapshot_spare`) equal to the slots added. In addition each child checks all of it against the model (a disagreement is a `VIOLATION`, exit 3, which fails the unit even when both arms agree).

## What the driver cannot see: mutations it could easily miss (for the mutation agent)

1. **The calling thread not taking part in the mapping** (15 helpers do all the work, the caller only waits), or any other split of the work among the 16 workers: only the number of `pthread_create` calls is checked, not which thread called `mmap`.
2. **The seconds in the summary line:** only the shape `%.1f s` is checked, so a timer started after the mapping, in the wrong unit, or a constant `0.0` goes unseen.
3. **Registering / spare-adding chunks in the opposite order together:** chunk identity in the log is the registration order (the address that belongs to `base[i]` depends on which thread mapped it, which is free), so reversing the register loop *and* the spare loop gives the same log. Reversing only one of them is caught (probe B is of that kind).
4. **Stderr written in several `write` calls, or with an extra flush,** and **extra calls of `error_string`** (the fake does not count them) are not observed.
5. **Values that need a real large mapping:** `bytes >= 2^32`, `n_chunks > 24`, chunk sizes above 4 MiB (e.g. a 32-bit truncation of `chunk_bytes` or `cap_slots` inside `host_init` while `plan()` stays right). `host::plan` and the summary line are unit-tested with the real numbers (150 GiB, 561512448-byte chunks), but the end-to-end path never maps more than 48 MiB.
6. **A pool with more than 4000 slots:** the largest accepted pool in the units has 4000 slots (1300 with the real constants), so a cap on the number of spares above that goes unseen.
7. **State kept between calls** of more than three: M runs at most 3 steps per process.
8. **Out-struct writes at other moments on paths that return normally** (the contract only fixes the moments for a process that exits; the driver sees the struct only at the end, or at the exit): a mutant that stores `slots` after the refusal test is caught (the refusal path is a fatal exit with `slots` visible); one that stores `base` before vs after the malloc op is not, because the fake stores through the pointer as well on a failed call.
9. **A helper-thread stack size, a different madvise return handling, `MADV_HUGEPAGE` skipped when THP is unavailable** (the call must be made; its result is ignored): the result of `madvise` is not varied (the real syscall decides).
10. **Memory behaviour:** leaks, double mapping hidden by the interposer's counts (counts are checked), unmapping at the end (the original never unmaps; a mutant that unmaps would fail the memory check only if it did so before the driver's check).
11. **Data races** between the helpers (TSan not run) and a spurious failure on a heavily loaded box (the driver was not run with injected scheduling noise).
12. **`ready` / `cap_slots` semantics seen by the engine** (e.g. `cap_slots` untrimmed at the exit, trimmed at the return) are checked at both moments, but not through the engine's own `atexit` summary.

## Not verified

- Nothing was run on a GPU or against the CUDA runtime; the engine was not run with this library (no integration was made).
- The real engine constants for the host cache (561 MB chunks, 150 GB): only arithmetic (unit tests) and the 0-chunk call; no real mapping with those sizes.
- No ASan / UBSan / TSan / Valgrind run on either library; the Rust library was not run under Miri.
- The driver's model is written by the same author as the harness and the crate (from decode.cuh@4d8d891); the extraction text is the only part taken byte for byte from the original.
- Behaviour outside the contract (negative `experts`, a table of chunks that cannot be allocated, a failing thread start).

**What the driver does now, per gap** (every check is only a *violation* when it fails; the first failing line of each mutant is in the table of `mutants/RESULTS.md`, section "Driver v2"):

| gap (mutants) | check added to `pi_driver.cpp` | why it is built this way |
|---|---|---|
| Seconds of the summary line (M11-M15) | `clock_gettime` is now also defined in the driver. During a host call `CLOCK_MONOTONIC` returns the real reading plus a **virtual** offset that grows by fixed amounts: 0.3 s per `mmap`, 0.2 s per `host_register`, 0.1 s for `set_device`, 0.1 s per 32 `sc_add_spare` calls (one per chunk). The library's own timer therefore has to print `0.6 * n_chunks + 0.1` s plus its real elapsed time; required: `round1(V) <= printed <= round1(V + wall time of the call)`. Every other clock id is shifted by +1000 s per reading. | The study proposed real 60 ms sleeps in `mmap` (lower bound 0.1 s in all). Virtual time was used instead: the bound is 0.6 s per chunk, it is exact whatever the thread schedule, it costs no wall time, and a loaded box cannot fail it (the upper bound is the measured wall time of the call). It also covers a timer stopped before the registration or the spares, and a nanosecond scale error. **It assumes the library reaches `clock_gettime` through the dynamic linker, as the reference and the crate do**; a library that made the raw system call would print about 0.0 and fail (the header says "wall time (CLOCK_MONOTONIC)", not how it is read). |
| The calling thread must map when there are >= 16 chunks (M03) | Gate 1 (barrier), for host steps with >= 16 chunks: the first `mmap` of each thread waits until 16 distinct threads are inside `mmap`; afterwards 16 distinct threads must have mapped, the calling thread among them. A barrier not filled within 5 s (real) is released and reported (`gate 1 ... timed out`). | With the barrier each of the 16 workers holds exactly one chunk, so the result does not depend on who is faster (the study measured that the caller maps something in only 15% of the >= 8-chunk units of the original). |
| Registration order across units (M33, M46) | Gate 2 (serial), 30% of the host steps with >= 2 chunks (drawn from a separate random stream): a `pthread_create` trampoline holds the 15 helpers until the calling thread has made its n-th `mmap`; the caller then takes chunk numbers 0, 1, 2, ... from the counter in order, so the i-th `host_register` must be the address returned by the i-th `mmap`. A caller that does not map every chunk times out after 5 s and is reported. | **Deterministic per unit, not statistical.** The study could only show a shift of an order statistic (ascending in 368 of 724 multi-chunk units against 4 in the original), a property of the kernel's placement and of a race. With the helpers held back, the order in which the chunks are taken from the counter is the order of the `mmap` calls, so the contract's "base[chunk number] = p, register i = 0 .. n-1 in order" becomes observable in a single unit. The held-back schedule is one the original really can have (helpers that start late). Free-running steps stay as they were. |
| `error_string` called twice (M57) | The fake counts its calls per step: exactly one per failed CHECK, none otherwise. | The original's `CHECK` evaluates `cudaGetErrorString(e)` once; the reference passes this. |
| Stderr written with two `write()` calls (M58) | fd 2 of a child is one end of a non-blocking `SOCK_SEQPACKET` socketpair, so every `write()` on stderr arrives as one record (C `fprintf` and Rust's std alike; what arrives is also appended to the `.err` file as before). A message of up to 100 bytes must arrive in exactly one record; no message, none; a longer message: at least one. | **Finding: the reference itself writes a long message in several chunks** (glibc 2.39 flushes an unbuffered stream about every 128 bytes; measured with a small C program: a 100-byte file name gives 1 write, 110 gives 2, 240 gives 3). "One message, one write" is therefore the original's behaviour only for short texts, and a stricter check fails the control (it did, on the first try: the reference failed 8 of 50 HX units with 2 writes). M58 is caught in the units whose message is short only. |
| Unbounded event recorder (found hazard) | Every recorded call goes through one function with a hard cap of 200,000 records per step (a legitimate step makes about 4,200 at most); past it the unit fails with `VIOLATION event recorder cap ...` (exit 3) before anything more is recorded or handed to the real slot cache. | A library that returns an absurd slot count (M69, M70, M108) made the recorder grow past 14 GB per child. The `ulimit -v` 3 GB cap used by the scripts is still applied, but is no longer what ends the unit. |
| Crash handler | `prctl(PR_SET_DUMPABLE, 0)` in every child. | A crashing child no longer starts `apport` (about 8 s per crash); the signal is still delivered and the unit still shows `sig6` / `sig11`. The study used an `LD_PRELOAD` shim for this. |
| Unit-test-only mutants M120, M121, M122 | New scenario `A` (`--scn A`, 60 units, **not** in the default run): the library's own refusals, called with NULL `ops` / `cfg` / `out`, one NULL function pointer, `expert_raw == 0`, alone (seeds 1-20: every defect of the header's list once, host and pool) or in groups of up to three (seeds 21-60). Expected: `poolinit: <the first defect in check order>\n`, exit 1, no op call, no `mmap` / `madvise` / thread, out struct untouched; the reference has the same texts (`ADAPTED (6)` in `poolinit_ref.cpp`), so the two logs are also compared byte for byte. | Cheap (a unit is two processes that end at once). The texts are the crate's own and the reference's own (the header only says `poolinit: <what>`), so the check pins the crate to the reference, not to the original text. |
| M117 (`pi_expert_stats` field order) | **Nothing added; not closable in the driver.** The `.so` of M117 is byte for byte the `.so` of the unmodified crate (md5 `b5cba5c4`), because nothing reads or writes `st`: no test of the binary can tell the two apart. `cargo test` (`struct_layout_equals_the_c_header`), which `final.sh` runs, is the check. | |
