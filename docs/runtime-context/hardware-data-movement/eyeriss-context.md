## 2. What this is
Authors say (Chen, Emer, Sze, ISCA 2016, Abstract and Section V; Chen, Krishna, Emer, Sze, JSSC 2017, Sections I and III-V): Eyeriss is a spatial architecture accelerator for deep convolutional neural networks with 168 processing elements (PEs, arranged as a 12x14 array), a 108 KB on-chip global buffer (GLB), a custom multicast/point-to-point network-on-chip (NoC), and off-chip DRAM with run-length compression (RLC). Authors say (ISCA 2016 Section V-A, JSSC 2017 Section IV-A) it introduces the row-stationary (RS) dataflow, which breaks high-dimensional convolutions into 1D convolution primitives (one filter row of length $S$ convolved with one input feature map row of length $W$ to produce one partial sum row of length $F$). Each 1D primitive runs stationary inside one PE using three local scratchpads (filter SRAM spad of 224x16b, ifmap register spad of 12x16b, psum register spad of 24x16b), while a 2D convolution is mapped onto a logical PE set of $R \times E$ PEs where filter rows are reused horizontally, ifmap rows are reused diagonally, and partial sums accumulate vertically across adjacent PEs. Authors say (ISCA 2016 Section VI-C, Table IV) this four-level storage hierarchy (RF/spad $1\times$, inter-PE array $2\times$, global buffer $6\times$, DRAM $200\times$ relative to a 65nm MAC) minimizes total data movement energy by exhausting reuse at the lowest-cost local levels before accessing higher-cost levels. The community repository `mmdnmz/Eyeriss` provides Verilog/SystemVerilog modules for a PE, scratchpads, FIFOs, counters, array wrappers, and an unfinished cluster controller.

## 4. How it works
(What I understood from running it. Paper text is cited by file; RTL claims cite an experiment.)

**The problem the papers address** (`eyeriss_isca_2016.txt` lines 215-300, read): a CONV layer is $O[z][u][x][y] = B[u] + \sum_{k,i,j} I[z][k][Ux+i][Uy+j]\,W[u][k][i][j]$; each weight is reused $E^2$ times, each ifmap value up to $R^2$ times, and $C R^2$ psums reduce to one output. Maximum input reuse and immediate psum reduction cannot both be had (the psums that share a weight or ifmap value are not reducible), so a dataflow is a choice of what to hold still and what to move.

**Three existing dataflows** (ISCA 2016 section IV, read): WS holds each weight in a PE register and streams ifmap pixels past it; psums are accumulated across PEs. OS holds each output's psum in a PE and streams weights and pixels to it. NLR keeps nothing in the PE. In the RTL I ran (E4): WS wrote each weight once (`9` writes for `81` MACs) but wrote ifmap values once per MAC and did `72` inter-PE adds; OS wrote weights and pixels once per MAC and did none.

**Row stationary** (JSSC 2017 lines 262-300 and 385-410, read; ISCA 2016 section V): split the convolution into 1-D primitives (one filter row, one ifmap row, one psum row) and give each to a PE; filter rows are shared horizontally, ifmap rows diagonally, psums accumulate vertically. A PE with $p\times q$ primitives interleaved holds `p*q*S` filter words, `q*S` ifmap words, `p` psums. In the RTL (E3) the 2D convolution on an $R\times E$ grid matched the golden on every pixel, with `1/E` filter-spad writes per MAC and `(R-1)/R^2/C` inter-PE adds per MAC; increasing $E$ (bigger ifmap), $C$ and $M$ each lowered one of the per-MAC counts.

**What the PE is** (E1, E2, E6 source reading): three scratchpads (ifmap register file, filter SRAM, psum register file; shipped sizes 12, 224, 24 words), input FIFOs with a `BufferController`, a counter-driven read schedule, a multiplier pipeline, `Zero_buffer`/`Disabling_mech` that gate the operand latches and the psum write when an operand is zero (E2: both spads are still read; operand latches 3 of 4 and psum writes 3 of 4 for one zero weight), and an output FIFO.

**What does not work as shipped** (E1, E2, E4, E6): `psum_mux_out` is never driven so `data_psum_out` shows `zzzz`/`0000` (E1; confirmed by me: declared at `PE.v:81`, used once at `PE.v:514`); `Custom_counter` saturates instead of wrapping so a second row uses the wrong weight (E2); the reset does not clear `loc_en`, `read_addr_change` and `mul_valid` (E2); `counter.v` wraps at literal `3'd7` (E4; confirmed at `counter.v:27`); the cluster does not match the PE (E6).

## 5. What surprised me and what I got wrong
- **Predictions that missed (E1)**: undriven wire gives `zzzz`, not `xxxx`; only the first 4-element window of `psum_spad` is a true dot product.
- **Predictions that missed (E2)**: a 1-cycle `weight_write_en` strands the last weight; post-reset psum writes land in `regs[1..2]` until three registers are reset.
- **Prediction that missed (E3)**: sparse run gated 16 MACs, not 15 (an ifmap row is multicast to two PEs, so one zero gates two MACs).
- **My review of the agent's E3/E4**: the counts matched formulas I could derive from the loops, which is a weaker statement than 'the RTL implements row stationary'. The testbench drives the schedule (E5).
- **Stored E3 result was stale**: the E3 script has 8 runs; the stored output had 7. Re-running added `R=3, H=7x7` (`E=5`: `w_wr=45`, `i_wr=105`, `vert_add=50`), which matches the model. I replaced the stored output with the fresh one.
- **I assumed `PE_Cluster.v` might be repairable with stand-ins**; running showed the problem is a different PE port set (E6).
