The Clover HG Format

Convert any open-weight model to run on CPU — ~4× smaller, up to 5× faster tok/s, ~98–99% of BF16 accuracy.

On CPU, language model speed is bottlenecked by moving weights across memory wires, while naive 4-bit or 2-bit quantization clips outlier channels and breaks math and code reasoning. Clover’s Hadamard-Grouped (HG) conversion process rotates every 128-weight block through a column-balanced Fast Walsh–Hadamard Transform (FWHT-128), quantizes to a 1-cycle register Gaussian codebook (LUT16) in a 16-row SIMD layout (4.125 bpw), and pairs weights with lossless precomputed operator sidecars (HG4OP001) — running with zero GPUs, zero CUDA, and zero PyTorch at runtime.

Part 1 — How the HG conversion process works (for any model)

Trained neural networks concentrate activation and weight energy into a handful of sharp outlier channels (10×–50× larger than neighboring coordinates). In standard block quantization, one outlier forces a wide scale factor that crushes all neighboring weights toward zero. The Clover HG process eliminates that failure mode in four training-free steps:

Honest precision contract: what is near-lossless vs. what is 100.0% bit-exact

Real-world mental model: Phone S23 (8 GB) → Laptop (16 GB) → Server (128 GB) → RTX 4090 (24 GB)

Take one concrete model — LFM3-Omni-2B (3.22 GiB in BF16, 0.83 GiB in HG4-16R) — and run it across four real devices. Everything about memory, GPUs, and tok/s comes down to three physical facts:

Decode tok/s  ≈  Active Memory-Wire Speed (GB/s)  ÷  Active Bytes Moved per Token (GB)
  • 1. “OOM” only happens in naive all-at-once loaders — layer & expert switching runs in any RAM size: You only ever need RAM for one layer’s activations plus one layer’s active weights (< 500 MB). Even a 2.8T model (792 GB) can run in 2 GB RAM by streaming layers off SSD (pread + POSIX_FADV_DONTNEED); smaller RAM never forces a crash — it simply drops unpinned layers from RAM wire speed (67–75 GB/s) down to storage wire speed (4.22 GB/s measured on S23 UFS 4.0; 7–14 GB/s on NVMe).
  • 2. Why an 8 GB Samsung S23 phone (33.4 tok/s) beats a 16 GB laptop (12.4 tok/s), and why 128 GB adds 0 extra tok/s over 2 GB: Once 0.83 GiB fits in RAM, unused capacity does nothing (MemoryMax=2G vs. 124 GiB on the same server both measured 48.7 tok/s). The 8 GB Galaxy S23 runs 2.7× faster than the 16 GB Intel i7 laptop because S23’s LPDDR5X (67.2 GB/s + ARM DOTPROD) moves bytes faster than the 15W laptop’s DDR bus (~25 GB/s).
  • 3. Phone/Laptop Unified GPU (0 GB separate VRAM) vs. Discrete RTX 4090 (24 GB GDDR6X + System RAM):
    • Phone (Adreno 740) & 16 GB Laptop (Intel UHD, uma: 1) share system RAM: There is no separate VRAM chip (Windows exposes up to ~8 GB of the 16 GB RAM to the iGPU; Android caps single OpenCL buffers near ~2 GB). 0.83 GiB LFM3-Omni-2B fits easily in both: using the laptop iGPU speeds up compute-heavy prefill (204.7 tok/s Vulkan vs. 63.7 tok/s CPU), while decode hits the exact same shared RAM wire (12.83 tok/s Vulkan iGPU vs. 12.38 tok/s CPU). Putting “trunk in iGPU + experts in RAM” on unified memory moves zero bytes onto a faster bus.
    • Discrete GPU (RTX 3090 / 4090, 24 GB dedicated 1,008 GB/s GDDR6X + System RAM + NVMe — measured live on 1×, 4× & 8× RTX 4090): Here VRAM is 13× faster than CPU RAM! Models ≤ 18 GiB fit 100% inside 1× 24 GB GPU (LFM3-Omni-2B uses 854 MiB VRAM at 240.2 tok/s decode / 4,632.9 tok/s prefill with 87/87 bit-exact CPU parity; Clover-35B fits in 17.16 GiB VRAM at 168.35 tok/s vs. 12.79 tok/s PCIe-offloaded BF16 — 13.2× faster on 1× 4090!). Even when forced into Trunk-in-VRAM + Experts-in-RAM, Clover-35B needs only 1.68 GiB VRAM to hit 45.58 tok/s, Nemotron-120B hits 45.79 tok/s on 1× RTX 4090 (and 172.22 tok/s all-in-VRAM on 4× 4090), and Kimi-K3.1-Pro 2.8T reaches 7.89 tok/s by overlapping 150 GiB VRAM + 405 GiB RAM + NVMe simultaneously.

Step 1 — Optional C11 OpenMP Fast Packer (60–100× Faster for Large Checkpoints)

For 30B+ checkpoints, compile hg4_fast_packer.c so FWHT-128, 5-point guarded FP16 scale search, and 128-step Cholesky LDLQ run in parallel C11 AVX2+OpenMP across all cores.

gcc -O3 -march=x86-64-v3 -mavx2 -mfma -f16c -fopenmp -fPIC -shared \
  clover-ai-system/src/models/clover-35b-a3b/hg4_fast_packer.c \
  -lm -o libhg4_fast_packer.so

Step 2 — Pack Linear Projections into HG4-16R & Verify Cosine ≥ 0.995

convert_to_hg.py writes every 2D projection into weights/*.hg4 (magic HG4R), keeps 1D norms/biases/SSM states in exact FP32 inside passthrough.safetensors, and logs per-tensor cosine similarity, SQNR, and SHA-256 digests in hg_manifest.json.

Step 3 — Choose Single-Tier RAM (--moe-cold-bits 4) or Two-Tier RAM+NVMe (--moe-cold-bits 2)

If the converted model fits inside 80% of available RAM, keep everything in HG4-16R and mmap it. Only when total expert bytes exceed RAM should you enable --moe-cold-bits 2 --hot-experts H to pin hot experts in RAM and stream cold experts from NVMe via pread + POSIX_FADV_DONTNEED.

Step 4 — Emit Lossless precomputed_ops/ (HG4OP001)

Router matrices are pre-rotated in exact FP32 into precomputed_ops/*.hgop (or extended with architecture-specific RoPE/SSM tables via precompute_hg4_operators.py), verified to Top-K Jaccard == 1.000000.

Step 5 — Compile the C11 Engine & Serve via the OpenAI-Compatible /v1 Gateway

Compile your model family’s C11 engine with -ffp-contract=off (reference implementations in clover-ai-system/src/models/) and launch gateway.py to expose standard /v1/chat/completions SSE streaming with Longest-Common-Prefix (LCP) cache reuse for OpenCode, VS Code, or curl:

# Launch the standalone /v1 gateway on CPU (includes LCP prefix cache + exact x-cruncher math):
export OMP_NUM_THREADS=16
python3 clover-ai-system/src/tools/hg4-fusion-gateway/gateway.py \
  --mode real --host 127.0.0.1 --port 8790

curl -s http://127.0.0.1:8790/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"default","messages":[{"role":"user","content":"Write a binary search in Python."}],"temperature":0}'
