The Clover HG Format

Solving AI’s data-movement bottleneck: ~4× smaller models that fit in smaller RAM & VRAM, decode up to 45× faster, and preserve BF16 reasoning.

Modern language models are bottlenecked not by math speed, but by data movement — every generated token must haul gigabytes of 16-bit BF16 weights from memory into the processor. Standard 4-bit or 2-bit compression shrinks those weights, but a handful of extreme outlier channels clip the quantization grid and break code and math accuracy. Clover’s Hadamard-Grouped (HG) format solves both problems at once: it rotates every 128-weight block through a Fast Walsh–Hadamard Transform (FWHT-128) to erase outlier spikes before rounding into a register lookup codebook (4.125 bpw), keeping models compressed all the way into CPU and GPU registers.

1. Introduction — What is HG, why it is important, and how it works

Why do large AI models feel slow even on powerful processors? Because generating one word requires reading every active weight across a narrow memory wire. Naive low-bit formats try to shrink that wire traffic by rounding raw weights directly, but neural networks store critical reasoning features inside sharp outlier spikes (10×–50× larger than neighboring weights). One spike stretches the rounding scale and wipes out hundreds of nearby weights.

1. Smooth Outliers (FWHT-128)

Before any rounding happens, HG multiplies each 128-weight block by random sign flips and an orthogonal Hadamard matrix (H128). Every 30× spike is spread evenly across all 128 coordinates into a clean bell curve (0.996+ cosine vs. 0.923 for naive INT4).

2. Compute in Registers (LUT16)

Because (W D-1 H128)(H128T D x) = W x, we rotate the tiny input vector x once at runtime and multiply directly against 4-bit Gaussian indices (HG4-16R, or 2-bit HG2-16R for cold MoE experts) inside 16-row SIMD registers — never expanding weights back to BF16 in memory.

3. Keep Control Paths Exact (FP32)

Small, sensitive tensors — 1D RMSNorms, SSM state decays, and Hadamard-rotated Mixture-of-Experts router gates (HG4OP001) — stay in exact 32-bit FP32, guaranteeing 100.0% lossless expert routing (Top-K Jaccard = 1.000000).

2. Compression achieved across 4 models — BF16 size vs. HG size and why it matters

We converted and published four open-weight models spanning three orders of magnitude — from a 2B mobile/laptop model up to a 2.8 Trillion parameter frontier MoE. Decreasing model size by 2×–4× accomplishes two things simultaneously: (1) each token moves up to 4× fewer bytes across memory wires, and (2) models stay inside fast local RAM or GPU VRAM instead of spilling onto slow SSD or PCIe buses.

Output fidelity: deterministic BF16 parity & bit-exact cross-device execution

Shrinking a model only matters if its answers remain trustworthy. Under greedy decoding (Temperature = 0), HG4-16R reduces perplexity drift 8.0× below standard Q4_0 (29.06 vs. BF16 28.81, compared to 30.78 for Q4_0), produces character-for-character identical code and exact math answers to official BF16 PyTorch, and executes 100.0% bit-identically across x86 CPU, ARM64 mobile, and RTX 4090 CUDA (87 / 87 matching tokens; minor wording differences vs. BF16 appear only on open-ended prose):

5. Conclusion & recommendations — adding more RAM or VRAM does not solve AI’s data-movement problem

The clearest finding across our phone, laptop, Hetzner CPU server, and 8× RTX 4090 experiments is a simple physical law: buying more RAM capacity (GB), more VRAM capacity (GB), or faster compute cores adds +0.0 tok/s to token decoding once a model fits in memory.

Our recommendations: how AI systems should actually solve data movement

Because stacking larger RAM/VRAM chips or bigger compute dies leaves the memory-wire bottleneck untouched, sustainable AI inference requires attacking data movement directly on both the model side and the hardware side:

1. Smaller, Domain-Expert Models & Sparse Routing

Stop hauling multi-hundred-gigabyte monolithic dense weights for routine tasks. Pair compact, specialized models (2B–35B in HG4) with fine-grained Mixture-of-Experts (MoE) that activate only the tiny subset of domain experts needed per token, plus lossless multi-token verification (MTP / DSpark) so one weight read produces 3–4 tokens.

2. In-Memory Processing (PIM) & Near-Memory Compute

Instead of shuttling weights across centimeter-long PCB traces and PCIe buses on every token, move multiply-accumulate units inside or directly beneath memory arrays — DRAM Processing-in-Memory (HBM-PIM, LPDDR-PIM), 3D wafer-on-wafer Hybrid Bonding (SRAM/DRAM stacked directly on logic), and CXL near-memory engines.

3. Multi-Channel Buses & Register-Level Compression

Favor more parallel memory channels (dual/quad/octa-channel LPDDR5X / HBM and multi-GPU Tensor Parallelism) over single wide-capacity sticks, and keep weights in Hadamard-compressed form (HG4-16R) all the way into processor registers with stateful prefix caching (LCP) so neither weights nor context move twice.
