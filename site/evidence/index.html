Evidence

From the first production case studies to clover-kimi-k3 — what was checked, what was observed, and where each piece of work stopped.

In Clover, an Outcome is confirmed by the real environment rather than a confident summary. Every entry on this page states what was tested, what the system actually showed, and the exact boundary where verification stopped—without rounding test results up into production claims.

Read the storyline below in order: starting with two production case studies (a Contentful API migration and an upstream React Server Components memory leak), moving through three organizational reference implementations and five field lessons learned from real work, and culminating in clover-kimi-k3—our 7-layer neuro-symbolic, compiler-verified, and memory-accumulating AI system evaluated head-to-head on 8 × NVIDIA RTX 3090 GPUs.

Everything recorded here is software and AI systems engineering, because that is where the author works. The Clover cycle applies to any system, and if you run and verify a cycle in another field, the repository is where it belongs.

Evidence 1 of 5 · Production Case Study · API Migration

Contentful API migration

A CMS content API rewritten from a GraphQL integration to REST, and from .NET 9 MVC to .NET 10 Minimal APIs, with every route, JSON shape, and response envelope preserved so no consumer had to change.

A manual rewrite was estimated at 8–10 weeks of team effort. With AI carrying most of the implementation under close human direction, the implementation took about a day. Parity was checked across 36 endpoint cases: 34 matched exactly and 2 were signed-off deviations, alongside 239 tests. Both versions ran in the test environment with the API gateway pointing at the new one, so QA validated the real site and signed off. The production cutover has not run.

Read the case study →

That day is implementation only. Testing and parity validation took roughly another day, and stakeholder agreement longer still, and the work was not continuous. Comparing one day against a ten-week estimate that included analysis and coordination would overstate it.

Performance was measured locally, two processes on one machine, and never on deployed infrastructure. The gains came from the architecture rather than from AI.

What matters here is how much AI lowered the barrier to attempting the work at all, rather than who wrote the code.

Evidence 2 of 5 · Production Case Study · Upstream Root Cause

A React Server Components memory leak, traced upstream

A production application was crashing with out-of-memory errors. A blunt Node flag stopped the growth and stabilized production, and it also stripped error-stack detail everywhere. The mitigation was validated on a fleet running the same image: 113 restarts without the flag, zero with it, over about six and a half hours.

The investigation continued past the workaround, traced the retention mechanism into React's react-server renderer, and produced a one-file fix contributed upstream so other applications need not carry the same workaround.

Evidence 4 of 5 · Field Lessons · What the Early Cycles Taught

Five lessons from running this on real work

These came out of the work above, including the parts that went badly. The evidence behind each one is software; the lesson is not.

Focus beats parallelism
Agents made it easy to run three initiatives at once, and context and human direction spread too thin across all of them. Dropping the parallelism and working one stream at a time is what finally resolved the hardest issue at its root. Human attention is the scarce resource, rather than AI throughput.
Read the system before fixing it
AI jumped straight to attempted fixes and repeatedly failed, because each attempt was a guess. Gathering what the system was really doing end to end, and adding logging where the picture had holes, found the root cause far faster than the fix-first thrashing that came before it. Thrashing is the signal to stop fixing and go back for the information.
A workaround is not the destination
Disabling stack-trace capture stopped the production memory growth, and that was the right immediate mitigation. Continuing past it found the retention mechanism underneath and produced an upstream fix instead of a workaround carried forever. Ask what a workaround is hiding or disabling, rather than only whether the incident stopped.
You do not have to hold the context to be accountable for it
A defect arrived in a flow the responsible human had never worked on. The orchestration layer read across the repositories, reproduced the behavior in the running application, and showed where it happened. The knowledge was in the system the whole time. Treat "I am not current on this area" as a question about access. Accountability stayed with the named human throughout.
Write the context down, or pay for it again
Two investigations, the same human, the same tools, the same period. The one that kept findings written down beside the work converged. The one where nothing persisted between passes degenerated into repeated attempts at a fix. A file maintained during the work is memory; a write-up produced afterwards is a report. That write is Growth, the fifth stage of the system cycle, and what it keeps becomes the next cycle's Context.

These share a root. AI multiplies whatever Context and Direction it is given. Teams that read the system first and then say what they want get outcomes that hold up, and teams that skip the reading get a lot of output and few outcomes.

Evidence 5 of 5 · clover-kimi-k3 · 7-Layer Neuro-Symbolic, Compiler-Verified & Memory-Accumulating System (v4)

clover-kimi-k3

(7-Layer Neuro-Symbolic, Compiler-Verified & Memory-Accumulating System — Clover AI v4)

clover-kimi-k3 is a local open-weights AI system built under the Clover cycle (Context → Direction → Execution → Outcome → Growth). Rather than relying on a raw language model alone, it surrounds a 93-layer 2.78-trillion-parameter Mixture-of-Experts backbone and an 8B reasoning planner with verified tools, statement-by-statement compiler checking, a deterministic symbolic ontology, and a persistent file-based memory graph.

What our head-to-head evaluation shows in plain terms: On a 70-task benchmark suite spanning general knowledge (MMLU), math (GSM8K), executable Python & Rust coding (HumanEval + rustc), structured output (Sudoku, WMT14, XSum), organization-specific ontology records, persistent memory, and multi-hop tool use, clover-kimi-k3’s underlying model on its own scores 33 / 70 (47.14%). Adding clover-kimi-k3’s tool orchestration and compiler-in-the-loop code checking raises that same model to 57 / 70 (81.43%), and adding clover-kimi-k3’s symbolic ontology and persistent memory graph brings it to 70 / 70 (100.00% pass rate, 99.08% mean score) while cutting GPU compute per solved task in half (234.0 → 114.5 GPU-s). Standalone frontier models (GPT-6 Astra and Claude Opus 5.5) are already near-perfect on the 58 public tasks without tools (56/58 = 96.6% and 57/58 = 98.3%), and only miss the private ontology and memory tasks whose records are not in their prompt. clover-kimi-k3’s value is not a bigger raw model; it is the system around the model.

clover-kimi-k3 System Lift (70 Tasks) (47.1% → 100.0%): Same underlying model on 8 × RTX 3090: 33/70 (47.1%) raw model alone → 57/70 (81.4%) with Tools & Compiler → 70/70 (100.0%) with Ontology & Memory (2.04× lower GPU-s/solved).

Frontier Models on Public Tasks (96.6% – 98.3%): On the 58 public tasks (zero tools), standalone Claude Opus 5.5 scores 57/58 (98.3%) and GPT-6 Astra scores 56/58 (96.6%) vs. 30/58 (51.7%) for clover-kimi-k3’s raw model alone.

93-Layer GPU VRAM Hit Rate (95.22% – 95.29%): 148.5 K3 tok/s across all 93 GPU layers (112.1 ms/layer), 0 PCIe D2H writebacks on cold/warm reads, and 8 Rust host crates verified bit-identical (max_abs_diff = 0.0).

Session & Batch Capacity (256K Context): 262,144 Kimi K3 tokens per session; clubs up to 8 concurrent sessions per GPU batch with 0 cross-session token leakage and 17,869.8 tok/s 8-GPU DDP NCM ceiling.

The seven layers of clover-kimi-k3

The model can propose; the system decides; the tools enforce; evidence verifies; humans remain accountable. clover-kimi-k3 implements that principle across seven layers that run on one CPU workstation or an 8 × NVIDIA RTX 3090 GPU server:

  1. Governance & Discernment Kernel (AGENTS.md): Operates under the five-stage cycle (Context → Direction → Execution → Outcome → Growth), keeping observed, externally_verified, hypothesis, user_stated_belief, and unresolved epistemic states distinct.
  2. File-Based Memory Tree & Relational Knowledge Graph (k3_memory_graph.py): Stores human-readable Markdown entries with YAML front matter across memory_tree/ (32 canonical seed entries, 65 typed cross-branch relationships such as corrects, refines, challenges, and unresolved_with) with a rebuildable graph index and a closed-loop staging/ promotion gate. Upgraded with six mechanisms from the 11 foundational AI papers (Origin): McCulloch–Pitts inhibitory veto + Minsky–Papert Order-$k$ “One-in-a-Box” conjunctions, Rosenblatt zero-sum $\gamma$-branch balance, Hopfield bipolar cleanup, Sutton $\text{TD}(\lambda)$ path credit, LeCun GTN logadd confidence, and Vaswani $h=3$ multi-head subspace retrieval with Krizhevsky LRN.
  3. Ontology-Guided Neuro-Symbolic GraphRAG & Symbolic Verifier (k3_ontology_graph.py): Keeps deterministic ontology graphs, 4 Horn inference rules, Newell–Simon CSm/VCt structural signature pruning, and edge provenance strictly separate from neural weights, supplying structured [E#] entity records and [P#] relationship paths and verifying formal mathematical, multiple-choice, and source-grounding constraints.
  4. HybridAgent Continuous <latent> Reasoning & Live Tools (k3_agent_engine.py): Runs 14 continuous <latent> reasoning steps (HybridAgent-8B-Agentic + K3NativeHybridLink 7,168 → 7,168), executes live <search> (arXiv, Wikipedia, DuckDuckGo, URL fetch) and sandboxed <python> (exact math, unit tests, matplotlib / SVG charts), and processes images through Kimi K3’s 27-layer MoonViT3d vision tower.
  5. On-the-Fly Generative Compilation for Python & Rust (k3_generative_compiler.py): Seals partial Python and Rust code prefixes at statement boundaries during generation, invokes Python AST/doctest checks and rustc --edition=2021, and rolls back the KV cache to the offending statement whenever a syntax, type, borrow, or specification error appears.
  6. 93-Layer 2.78T MoE GPU/CPU Engine, Validated Rust Host Path & Direction B Data Movement (libk3_gpu_experts.so): Executes Layer 0 (dense KDA attention + MLP) and 92 Mixture-of-Experts layers (69 KDA + 24 MLA attention trunks, 896 routed 4-bit experts per layer, 92 shared experts) alongside 8 Rust host-path libraries (slotcache, poolinit, supply, copyq, routetable, planner, loader, engcfg — 213/213 unit tests, max_abs_diff = 0.0 C++ vs. Rust parity) and five Direction B data-movement upgrades.
  7. 11-Pass Parallel Next-Concept Modeling (NCM) & Native Web / VS Code Surfaces (k3_chat_server.py): NextConceptTransformer (119.96M parameters) and K3-Native VQ-VAE (144.00M parameters) emit 64-token windows in 11 parallel passes across the Clover Web UI and native VS Code Agent extension.

What the 70-task evaluation actually shows

A 100.0% (70 / 70) pass rate on a mixed 70-task suite can easily be misread if it is placed next to published full-benchmark leaderboard scores without context. Published leaderboards evaluate thousands of questions on a single benchmark family (such as all 14,042 MMLU questions or all 1,319 GSM8K problems). Clover’s 70-task suite (run_real_ai_benchmark_suite.py) is a system-level test that combines 10-question slices of MMLU, GSM8K, and HumanEval with live Rust compilation, structured output, private organizational ontology records, persistent session memory, and multi-hop tool tasks.

To make the comparison fair and unambiguous, we ran the exact same 70 prompt strings through three frontier models (GPT-6 Astra, Claude Opus 5.5, and Gemini 4 Argon, where our harness called the raw model directly without attaching Clover’s tools, compiler, ontology, or memory layers) and through three controlled arms of Clover’s own underlying model on our freshly bootstrapped 8 × NVIDIA RTX 3090 server, scoring every output with the exact same frozen scoring harness (Cycle 10 full report & raw JSON artifacts):

Three clear conclusions for readers and AI agents

1. Frontier models are stronger raw models on public tasks (96.6%–98.3% vs. 51.7%)
On the 58 public tasks (MMLU, GSM8K, Python & Rust coding, Sudoku, sentence reconstruction, summarization, and multi-hop math), standalone Claude Opus 5.5 (57/58 = 98.28%) and GPT-6 Astra (56/58 = 96.55%) solve almost every problem purely in-weights with zero tools. When Clover’s own underlying model runs without Clover’s layers (Arm 0), it scores only 30/58 (51.72%).
2. Standalone frontier models miss private tasks because of missing Context, not missing intelligence
In Categories 5 and 6, five tasks ask about private organizational records (Harbourside Council Mill Road, Payments Database Postmortem #209, Aurora Distributed Storage v4.2) and prior K3 engineering measurements that are not in the prompt text. All three frontier models rightly refused to invent those figures. No model can answer questions about a system’s private reality without Context.
3. Clover’s value is the +52.86 pp system lift (33/70 → 70/70) on local open hardware
Adding <python>/<search> tool orchestration and statement-boundary Python/Rust Generative Compilation (Arm 1) lifts Clover’s local model from 33/70 to 57/70 (+24 tasks: fixing GSM8K 2/10 → 10/10, Sudoku 0/5 → 5/5, Agent QA 4/8 → 8/8, and 3 broken Python/Rust programs 12/15 → 15/15). Adding Ontology GraphRAG and the Persistent Memory Graph (Arm 2) adds the remaining +13 tasks (57/70 → 70/70: MMLU 7/10 → 10/10, XSum grounding 1/5 → 5/5, Ontology 2/6 → 6/6, Memory 4/6 → 6/6) while cutting GPU compute per solved task by 2.04× (234.0 → 114.5 GPU-s).
