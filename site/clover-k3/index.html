Clover Kimi K3: 2.78T exact on one workstation, interactive in seconds with HybridAgent + NCM

Kimi K3 has 2.78 trillion parameters (93 layers, d = 7,168, 163,840-token tiktoken.model vocabulary). clover-kimi-k3 runs all 93 layers bit-identically on one CPU workstation from NVMe, and pairs with our GPU concept-to-token pipeline (HybridAgent + NCM + Clover Kimi K3) on 8 × RTX 3090 GPUs to turn a 356-second CPU decode into a 2.13 to 5.30-second interactive chat (or 0.92 s per prompt when clubbed in a batch, and 17,869.8 emitted Kimi K3 tokens/s across all 8 GPUs).

Is your machine like ours?

We have run it on one machine. The set-up script checks the machine first and tells you what it finds, so you can run preflight on its own before downloading anything.

What Our workstation What the check requires
Operating system Ubuntu Linux, x86-64 Linux on x86-64.
Processor AMD Ryzen 9 7950X3D: 16 cores, 32 threads, AVX-512 AVX2 at least. Without AVX-512 it only warns, because we measured the speed with AVX-512 only.
Memory 124 GB A warning below 120 GB, a stop below 64 GB.
Disk Two NVMe drives in RAID1 About 1.4 TB (1,400 GiB) free for the dataset, on a local filesystem where direct reads work (O_DIRECT): not tmpfs, not a network share. Allow about 12 GB more for the open weights and the draft model.
Permissions root root, or a memory-lock limit set to unlimited (in a service: LimitMEMLOCK=infinity). The engine locks its always-used weights in RAM.
Kernel settings Transparent huge pages on madvise Huge pages on madvise or always; vm.max_map_count of at least 262144 (1048576 advised). Both only warn.
Software gcc with OpenMP, binutils, git, curl, Python 3 with venv The packages step installs them on Debian or Ubuntu when run as root. Elsewhere, install them yourself.

What the memory is used for

Plan on using all of 124 GB. About 53 GB holds the always-used weights, locked in RAM. Up to about 26 GB holds the recently used experts (16 per layer). The attention cache grows with the conversation: the default chat window of 8192 positions is roughly 19 GB. In our default-window chat check the machine showed 121 GB in use after the first turn.

On less memory, or without AVX-512, expect the defaults to need changing and the speeds on this page not to apply. We have not measured either.

Setting it up

The engine lives in one folder, clover-kimi-k3, in this repository. The model itself is not in the repository: the precomputed layers are a separate dataset on Hugging Face, and the rest comes from the original open weights. One script does the whole set-up and stops at the first step that fails.

  1. Pick where the dataset goes. It needs about 1.4 TB on a local NVMe filesystem. The default is under /opt/clover-k3; to use another drive, set DATASET_DIR.
  2. Run the script. 
    curl -fsSL https://raw.githubusercontent.com/santhoshsathish94/clover-framework/main/clover-kimi-k3/src/scripts/set-up-new-machine.sh -o set-up-new-machine.sh
sudo env DATASET_DIR=/mnt/nvme/computed bash set-up-new-machine.sh
    With no step names it runs every step in order. To run only some, name them: bash set-up-new-machine.sh preflight. Without root, add SKIP_PACKAGES=1 and install the software yourself.
  3. If a step fails, fix what it reports and run the same command again. Steps that are finished are skipped, and the downloads resume.
  4. Read the report. It is written to /opt/clover-k3/set-up-new-machine.report, and the script exits with status 0 only if no step failed.

What verify checks

This is the step that matters. Do not trust a speed from an installation that has not passed it.

  • Recorded prompts. Prompts 1, 4 and 10 of 34 recorded ones must give the recorded token ids.
  • Draft model. Speculative decoding with the draft model must give the same tokens as plain decoding.
  • The 1,000-token prompt. Its embeddings, layer 92 output and eight snapshots must match the reference chain bit for bit. This needs the reference values from the dataset; without them the check is skipped with a warning.
  • Chat. The second turn of a chat must remember a name from the first.

The result is written to src/work/results/verify-setup.result as lines starting PASS, WARN or FAIL. To run it again alone: src/scripts/verify-setup.sh from the engine folder.

Running the model

Run everything from the engine folder. One model run at a time: each uses nearly all of the memory.

cd /opt/clover-k3/clover-kimi-k3

# the recorded 1,000-token prompt, compared with the reference chain
src/scripts/run-model.sh recorded

# any text file as the prompt
src/scripts/run-model.sh text my-prompt.txt

# write 48 more tokens, keeping 16 experts per layer in RAM, and save their ids
PF_DECODE=48 PF_CACHE=16 PF_SAVE_IDS=reply.ids src/scripts/run-model.sh text my-prompt.txt
src/work/build/ids-to-text src/datasets/third-party/kimi-k3-open-weights src/work/results/reply.ids src/work/results/reply.txt

The first run builds the engine if the set-up has not. The logs and saved ids land in src/work/results. A short prompt took about a minute in our verify runs, because reading even a short prompt pulls in every expert it needs.

As a chat

One process keeps the model loaded and the conversation in memory, so a follow-up costs only its own tokens.

src/scripts/chat-start.sh mychat "Answer briefly."     # starts detached; wait for session-mychat/ready
src/scripts/chat-say.sh mychat "What is a KDA layer?"  # sends one message and prints the reply
src/scripts/chat-stop.sh mychat

chat-say.sh waits 60 seconds by default (WAIT=seconds changes it). A longer reply stays in session-NAME/reply-NNNN.txt and the script tells you where. In our checks a short follow-up took about 70 to 75 seconds in all. When the conversation outgrows the window, the oldest turns are replaced by a summary the model writes, which costs a prompt pass over the kept text and can lose facts.

With the draft model

PF_DECODE=48 PF_CACHE=16 SPECULATIVE_DRAFTER=dspark SPECULATIVE_DRAFT_TOKENS=8 src/scripts/run-model.sh text my-prompt.txt

The draft model proposes up to 8 tokens and the full model checks them in one pass, so the text is the same as plain decoding. It pays on code and repeating text and gains little on prose.

Tuning it to your machine

These are the settings that depend on the hardware, in the order we would look at them, with what we know about each. All of it was measured on our workstation only.

Threads
The line in src/scripts/run-model.sh that starts the program sets OMP_NUM_THREADS=16 with OMP_PROC_BIND=close and OMP_PLACES=cores. Change the 16 to your number of physical cores. On our processor 32 threads was slower than 16, and runs without pinning varied by seconds. We have not tested another CPU.
Expert cache
PF_CACHE is how many experts per layer stay in RAM between decode steps. We use 16 (about 26 GB). Lower it to fit a smaller machine; 0 turns it off.
Exact or faster
USE_4BIT_TRUNK=1 packs the always-used weights to 4 bits in RAM for decoding. Decoding goes from 3.1 to 3.5 s to 2.5 to 2.8 s per token, it needs about 29 GB more RAM (the trunk files are then not locked in memory), and the output is no longer bit-identical. The prompt pass stays exact. Leave it off to stay exact.
Draft model
SPECULATIVE_DRAFTER=dspark needs the 7.1 GB draft checkpoint. The draft width, 0 to 8 tokens, is chosen per pass from how many were right recently. A fixed width of 8 was 1.5 times slower than plain decoding on prose, so leave it to be chosen.
Chat window
PF_CONTEXT is the number of positions kept (8192, roughly 19 GB of attention cache) and PF_CHUNK the tokens per prompt pass (1024). A chunk of 2048 ran out of memory on 124 GB. Lower PF_CONTEXT on a smaller machine.
Where the data lives
DATASET_DIR, OPEN_WEIGHTS_DIR and DSPARK_DIR point the engine at data kept on a bigger drive.

When something fails

O_DIRECT does not work
The dataset is on tmpfs or a network share. Put it on a local NVMe filesystem and set DATASET_DIR.
Not enough disk
The check wants the missing part of the dataset plus 3% free. Point DATASET_DIR at a bigger filesystem.
Memory lock fails or the engine is killed
Run as root, or set the memory-lock limit to unlimited (LimitMEMLOCK=infinity in a service). Check that nothing else is using the memory, and lower PF_CACHE or PF_CONTEXT.
check-dataset reports missing files
The download is not finished. Run the download step again, then check-dataset.
A file has the right size but you doubt it
Run CHECK_HASHES=1 src/scripts/check-dataset-files.sh to compare every SHA-256 with the list.
The 1,000-token check was skipped
The reference values (engine-inputs/refs) were not in the downloaded dataset. Run download and then inputs again.
Build fails
The build log for each part is in src/work/build. Check that gcc supports OpenMP and that objcopy (binutils) is installed.

Where we started, and where it is now

We did not start from nothing. Fareed Khan's kimi-k3-in-c (Apache-2.0) is the engine that showed Kimi K3 could be run from C on one machine, and it is where we started: we ran it on our workstation first, measured it, and then asked what the model computes. What the input figure is
The prompt lengths differ between the rows (a dozen tokens, five, a thousand), so the input column is not a like-for-like ratio. A longer prompt is cheaper per token because every expert read serves more tokens at once.
What the output figure is
The draft model checks several tokens in one pass and keeps the ones that agree with the model's own choice, so the text is identical to plain decoding. It helps most where the text is predictable; on ordinary prose the gain is about 1.2 times (64 min 49 s plain against 54 min 5 s for the same 1,078 tokens). Nothing about this is interactive: 2.7 to 3.3 s per token is a different activity from chatting.
What is exact
With the default settings the 1,000-token prompt produces the same embeddings, the same layer 92 output and the same eight snapshots, bit for bit, as the reference chain it is checked against. The 4-bit trunk (2.5 to 2.8 s per token) is faster and is not bit-identical: on 34 recorded prompts it gave the same 12 tokens as the exact run in 8.
What it does not show
One workstation. One real prompt for the draft-model comparison, run once each. The first-version figures are recorded history from September, not re-run. Reply quality was read, not scored.

Fast GPU concept-to-token pipeline (HybridAgent + NCM + Clover Kimi K3)

On the 8 × RTX 3090 server (24 GiB VRAM per card, 376 GiB RAM), we connected continuous latent planning (HybridAgent-8B-Agentic for text and Qwen3-VL-8B-Instruct + HybridLink for images, d = 4,096) with a parallel 11-level Next-Concept Model (NextConceptTransformer, 119.96M parameters, d = 384) and a 3-layer pointer-generator decoder (K3LexicalPointerDecoder + K3-Native VQ-VAE, 144.00M parameters) re-anchored directly onto Kimi K3’s native 163,840-token tiktoken.model vocabulary and 7,168-dimensional embedding geometry (e8_k3_direct).

Instead of generating one token per forward pass, each 64-token Kimi K3 window is generated in 11 parallel coarse-to-fine VQ passes ([1, 4, 8, 14, 20, 26, 32, 40, 48, 56, 64] = 313 concept codes) conditioned on a 96-slot dual prefix (48 continuous HybridLink R(h) vectors + 48 discrete Kimi K3 BPE plan tokens). The output can either be returned immediately in Unverified Fast Chat Mode (2.17 to 5.56 s end-to-end from raw prompt, where the NCM + pointer-decoder stage itself takes 155 ms single-candidate or 402 ms for 8-candidate MBR8) or passed as PF_EXTRA into the 93-layer C engine for a single-pass verification.

Why DSpark was removed from the GPU pipeline
Ablating the 5-layer Dense MLA K3DSparkVerifier (7.12 GB, 8.95 s load) against plain adjacent-token deduplication across p1..p5 produced 0 differing tokens on 4 of 5 prompts (and 1 token on p2), with identical factual key recall (39/47 = 83.0%) and identical 48-token prefix match to the 93-layer engine. Removing it saved 7.12 GB of VRAM and 8.95 s of setup.
What unverified mode does not cover
Because K3LexicalPointerDecoder selects all 64 tokens per window in parallel (non-autoregressively) on top of a 313-code VQ bottleneck, rare domain words that were not in the VQ-VAE adaptation mix can still collide in VQ space if their base decoder logit exceeds the copy pointer boost (copy_scale = 18.4), and symbolic math equations (=, ×) can drop operators. When 100% 93-layer Kimi K3 fidelity is required, passing the generated token ids as PF_EXTRA into whole-model verifies the entire sequence in one batched pass.

How it is achieved, step by step

The unified pipeline replaces sequential 93-layer token-by-token generation with a six-stage concept-to-token architecture where every stage speaks Kimi K3’s native 163,840-token tiktoken.model vocabulary and 7,168-dimensional embedding geometry.

  1. Continuous <latent> reasoning and multi-turn memory (HybridAgent-8B-Agentic / Qwen3-VL-8B-Instruct + HybridLink, d = 4,096): When a prompt (and optional image or prior conversation turns) arrives, the planner enters continuous <latent> mode (token 151669) for 14 steps. At each step it passes its top-layer hidden state through the learned residual adapter HybridLink (R(h_t) = LN(h_t + W_2 SiLU(W_1 LN(h_t)))) and feeds that continuous vector directly back into inputs_embeds. For images (Option B), we measured a 0.9878 embedding cosine and 0.9453 top-layer hidden-state cosine between HybridAgent-8B-Agentic and Qwen3-VL-8B-Instruct, allowing HybridLink to graft directly onto the vision-language backbone.
  2. Structured two-window clause plan (W1 and W2) + R(h) extraction (~44 ms): After closing </latent>, the planner writes a compact two-line semicolon-separated factual skeleton (W1: and W2:, 25 to 36 words per window) containing the exact names, calculated numbers, and resolved pronouns from prior conversation turns, while extracting the continuous HybridLink vectors R(h) [W, 48, 4096].
  3. 96-slot dual-modality prefix packing (ComboBridge) and Optional Option A (MoonViT3d d = 7,168): In Cycle 46–48, within-checkpoint ablations proved that combining continuous R(h) vectors with discrete BPE plan tokens beats either modality alone (+0.07 retention over R(h)-only and −0.087 nats coarse code CE over BPE-only). ComboBridge(4096 → 384) packs 48 continuous R(h) slots alongside 48 discrete Kimi K3 BPE plan token embeddings (tokenized bit-identically via libk3tok.so). When Option A (--use-option-a) is enabled for images, Kimi K3’s native 27-layer MoonViT3d vision tower (model-00096) + PatchMergerMLPV2 (model-00095) runs in 42 ms to produce 225 × 7,168-d visual tokens for Kimi K3 token 163605 plus a 7168 → 384 visual prefix.
  4. 11-pass parallel coarse-to-fine concept generation (NextConceptTransformer, 119.96M parameters): Instead of 64 sequential steps per window, NextConceptTransformer predicts a hierarchy of 11 VQ concept levels of lengths [1, 4, 8, 14, 20, 26, 32, 40, 48, 56, 64] (313 discrete codes total) in 11 parallel forward passes, summing into quantized concept vectors z_hat [W, 64, 384].
  5. K3-native VQ-VAE (144.00M parameters, 163,840 vocab) and K3LexicalPointerDecoder: Fitting a ridge map from Kimi K3’s lm_head.weight [163840, 7168] to NCM’s d = 384 space across 95,367 shared byte pieces achieved 0.9542 cosine similarity, and 8-GPU adaptation brought exact VQ-VAE reconstruction on Kimi K3’s own p1..p4.ids to 460 / 467 (98.50%; 61 / 61 = 100% on p1b.ids) and 100% across chemistry, physics, medical, and math domain sentences. On top of z_hat, K3LexicalPointerDecoder (3 cross-attention blocks + ordered pointer head copy_scale = 18.4 + 2-gram subword continuation + ungrounded proper-noun/number mask + variable-length sentence-aligned K3_EOS) outputs all 64 Kimi K3 token ids in parallel, more than doubling exact number recall on val_500 (0.3427 → 0.7527, retention 0.9328).
  6. Clubbed batching across prompts and 8-GPU NVLink scaling (16K × 8 = 128,000 input tokens): By stacking $B$ independent prompts along the batch dimension ([B, seq_len] in the planner and [W_tot, 96, 384] in NCM with isolated per-prompt grounding masks), 8 prompts are answered together in 7.33 s (0.92 s/prompt, 94.25 tok/s, 0 cross-talk). Across all 8 RTX 3090s (where NVLink partner pairs 0↔2, 1↔3, 4↔6, 5↔7 transfer VRAM-to-VRAM at 51.9 GB/s one-way / 406 GB/s aggregate), 8-GPU DDP renders 256 windows in 641.5 ms (17,869.8 emitted Kimi K3 tok/s / 25,539.0 capacity tok/s).

The next experiment

Everything above is one workstation: a CPU, 124 GB of RAM and fast NVMe. The next run is on a smaller GPU server, rented by the week. It has not been run. This section is written before the run, so that what we expected and what we measure can be compared.

The machine, as listed
Ubuntu 24.04 Server; 8 × RTX 3090; 2 × Intel CPU, 24 cores at 4.0 GHz; 384 GB of RAM; “2000 NVMe”; a 10 Gbps port; 279 EUR per week excluding VAT. These are the provider’s words, not readings from the machine. The listing says “VRAM per card: 192 GB”, but NVIDIA gives 24 GB for an RTX 3090, so 192 GB is the total for eight cards. “2000 NVMe” has no unit, and the dataset alone is 1,399.8 GiB. The first step is to read the real figures from the machine.
Why it changes the experiment
The model does not fit. The routed experts are about 1,347 GiB (92 layers of 14.64 GiB each). The pruned trunk, 33.25 GiB, fits in the cards with room to spare. Video memory and RAM together, less the trunk and working space, would hold the experts of about 34 to 37 of the 92 layers (derived from the listing, depending on whether its GB are GB or GiB). The rest has to be read from NVMe for every token. So the question is less “how fast is the arithmetic” than “where do the bytes sit, and what moves them”. The engine is CPU code and nothing in it uses a GPU, so the first step is measuring, not porting.
Our direction
We think neither a CPU nor a GPU is the right shape for this work. What it needs is a new kind of tensor chip that computes next to its own memory: something like the tensor unit in a phone chip, which shares memory with the processor, but different, built for streaming a model’s weights rather than for graphics or for training. This is a direction, not a result. Nothing has been designed in hardware, simulated or built. Processing in memory, near-memory computing and unified-memory accelerators are existing lines of work; we have not surveyed them.
What supports it so far
One measurement on a CPU, with the earlier engine (kept in git history at commit 013cbc8): a decoded token took 3.07 s and moved 98.6 GB for 208 GFLOP of arithmetic, which is 2.11 FLOP per byte, and the arithmetic unit was idle about 82% of the time. The Kimi K3 technical report says the same of small-batch decoding: the expert matrix products reduce to memory-bound streaming of weights. The earlier design sketch is AI-PROCESSING-UNIT.md.
What it does not show
We have not measured a GPU. The claim is about decoding one stream of a model far larger than the fast memory. GPUs are effective for training and for serving many requests at once, where weights are reused, and we tested neither.
What we expect, written before the run
First, for layers whose weights are in video memory, the time per token will follow the memory bandwidth, not the arithmetic, and the arithmetic units will be mostly idle. Second, for layers that are not resident, the time will follow the transfer from NVMe, so adding cards adds little until the weights fit. We would change our mind if decoding turns out to be limited by arithmetic on the resident layers. Either expectation can be wrong, and the run will say which.
What we will measure first (proposed)
The machine’s real figures (cards, memory, NVMe size and speed, the links between them); the transfer rates NVMe to RAM to card; one layer’s expert read and projection on one card, in bytes per second and in operations per second; then the time per token with 0, 1, 2 and more layers resident.
