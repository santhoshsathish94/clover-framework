Clover

(7-Layer Neuro-Symbolic, Compiler-Verified & Memory-Accumulating System — Clover AI v4)

Clover is a local open-weights AI system built under the Clover cycle (Context → Direction → Execution → Outcome → Growth). Rather than relying on a raw language model alone, it surrounds a 93-layer 2.78-trillion-parameter Mixture-of-Experts backbone and an 8B reasoning planner with verified tools, statement-by-statement compiler checking, a deterministic symbolic ontology, and a persistent file-based memory graph.

What our head-to-head evaluation shows in plain terms: On a 70-task benchmark suite spanning general knowledge (MMLU), math (GSM8K), executable Python & Rust coding (HumanEval + rustc), structured output (Sudoku, WMT14, XSum), organization-specific ontology records, persistent memory, and multi-hop tool use, Clover’s underlying model on its own scores 33 / 70 (47.14%). Adding Clover’s tool orchestration and compiler-in-the-loop code checking raises that same model to 57 / 70 (81.43%), and adding Clover’s symbolic ontology and persistent memory graph brings it to 70 / 70 (100.00% pass rate, 99.08% mean score) while cutting GPU compute per solved task in half (234.0 → 114.5 GPU-s). Standalone frontier models (GPT-6 Astra and Claude Opus 5.5) are already near-perfect on the 58 public tasks without tools (56/58 = 96.6% and 57/58 = 98.3%), and only miss the private ontology and memory tasks whose records are not in their prompt. Clover’s value is not a bigger raw model; it is the system around the model.

The seven layers of Clover

The model can propose; the system decides; the tools enforce; evidence verifies; humans remain accountable. Clover implements that principle across seven layers that run on one CPU workstation or an 8 × NVIDIA RTX 3090 GPU server:

  1. Governance & Discernment Kernel (AGENTS.md): Operates under the five-stage cycle (Context → Direction → Execution → Outcome → Growth), keeping observed, externally_verified, hypothesis, user_stated_belief, and unresolved epistemic states distinct.
  2. File-Based Memory Tree & Relational Knowledge Graph (k3_memory_graph.py): Stores human-readable Markdown entries with YAML front matter across memory_tree/ (32 canonical seed entries, 65 typed cross-branch relationships such as corrects, refines, challenges, and unresolved_with) with a rebuildable graph index and a closed-loop staging/ promotion gate. Upgraded with six mechanisms from the 11 foundational AI papers (Origin): McCulloch–Pitts inhibitory veto + Minsky–Papert Order-$k$ “One-in-a-Box” conjunctions, Rosenblatt zero-sum $\gamma$-branch balance, Hopfield bipolar cleanup, Sutton $\text{TD}(\lambda)$ path credit, LeCun GTN logadd confidence, and Vaswani $h=3$ multi-head subspace retrieval with Krizhevsky LRN.
  3. Ontology-Guided Neuro-Symbolic GraphRAG & Symbolic Verifier (k3_ontology_graph.py): Keeps deterministic ontology graphs, 4 Horn inference rules, Newell–Simon CSm/VCt structural signature pruning, and edge provenance strictly separate from neural weights, supplying structured [E#] entity records and [P#] relationship paths and verifying formal mathematical, multiple-choice, and source-grounding constraints.
  4. HybridAgent Continuous <latent> Reasoning & Live Tools (k3_agent_engine.py): Runs 14 continuous <latent> reasoning steps (HybridAgent-8B-Agentic + K3NativeHybridLink 7,168 → 7,168), executes live <search> (arXiv, Wikipedia, DuckDuckGo, URL fetch) and sandboxed <python> (exact math, unit tests, matplotlib / SVG charts), and processes images through Kimi K3’s 27-layer MoonViT3d vision tower.
  5. On-the-Fly Generative Compilation for Python & Rust (k3_generative_compiler.py): Seals partial Python and Rust code prefixes at statement boundaries during generation, invokes Python AST/doctest checks and rustc --edition=2021, and rolls back the KV cache to the offending statement whenever a syntax, type, borrow, or specification error appears.
  6. 93-Layer 2.78T MoE GPU/CPU Engine, Validated Rust Host Path & Direction B Data Movement (libk3_gpu_experts.so): Executes Layer 0 (dense KDA attention + MLP) and 92 Mixture-of-Experts layers (69 KDA + 24 MLA attention trunks, 896 routed 4-bit experts per layer, 92 shared experts) alongside 8 Rust host-path libraries (slotcache, poolinit, supply, copyq, routetable, planner, loader, engcfg — 213/213 unit tests, max_abs_diff = 0.0 C++ vs. Rust parity) and five Direction B data-movement upgrades.
  7. 11-Pass Parallel Next-Concept Modeling (NCM) & Native Web / VS Code Surfaces (k3_chat_server.py): NextConceptTransformer (119.96M parameters) and K3-Native VQ-VAE (144.00M parameters) emit 64-token windows in 11 parallel passes across the Clover Web UI and native VS Code Agent extension.

What the 70-task evaluation actually shows

A 100.0% (70 / 70) pass rate on a mixed 70-task suite can easily be misread if it is placed next to published full-benchmark leaderboard scores without context. Published leaderboards evaluate thousands of questions on a single benchmark family (such as all 14,042 MMLU questions or all 1,319 GSM8K problems). Clover’s 70-task suite ([run_real_ai_benchmark_suite.py](https://github.com/santhoshsathish94/clover-framework/blob/main/clover-kimi-k3/src/tools/hybrid-ncm-k3/run_real_ai_benchmark_suite.py)) is a system-level test that combines 10-question slices of MMLU, GSM8K, and HumanEval with live Rust compilation, structured output, private organizational ontology records, persistent session memory, and multi-hop tool tasks.

To make the comparison fair and unambiguous, we ran the exact same 70 prompt strings through three frontier models (GPT-6 Astra, Claude Opus 5.5, and Gemini 4 Argon, where our harness called the raw model directly without attaching Clover’s tools, compiler, ontology, or memory layers) and through three controlled arms of Clover’s own underlying model on our freshly bootstrapped 8 × NVIDIA RTX 3090 server, scoring every output with the exact same frozen scoring harness (Cycle 10 full report & raw JSON artifacts):

Three clear conclusions for readers and AI agents

1. Frontier models are stronger raw models on public tasks (96.6%–98.3% vs. 51.7%)
On the 58 public tasks (MMLU, GSM8K, Python & Rust coding, Sudoku, sentence reconstruction, summarization, and multi-hop math), standalone Claude Opus 5.5 (57/58 = 98.28%) and GPT-6 Astra (56/58 = 96.55%) solve almost every problem purely in-weights with zero tools. When Clover’s own underlying model runs without Clover’s layers (Arm 0), it scores only 30/58 (51.72%).
2. Standalone frontier models miss private tasks because of missing Context, not missing intelligence
In Categories 5 and 6, five tasks ask about private organizational records (Harbourside Council Mill Road, Payments Database Postmortem #209, Aurora Distributed Storage v4.2) and prior K3 engineering measurements that are not in the prompt text. All three frontier models rightly refused to invent those figures. No model can answer questions about a system’s private reality without Context.
3. Clover’s value is the +52.86 pp system lift (33/70 → 70/70) on local open hardware
Adding <python>/<search> tool orchestration and statement-boundary Python/Rust Generative Compilation (Arm 1) lifts Clover’s local model from 33/70 to 57/70 (+24 tasks: fixing GSM8K 2/10 → 10/10, Sudoku 0/5 → 5/5, Agent QA 4/8 → 8/8, and 3 broken Python/Rust programs 12/15 → 15/15). Adding Ontology GraphRAG and the Persistent Memory Graph (Arm 2) adds the remaining +13 tasks (57/70 → 70/70: MMLU 7/10 → 10/10, XSum grounding 1/5 → 5/5, Ontology 2/6 → 6/6, Memory 4/6 → 6/6) while cutting GPU compute per solved task by 2.04× (234.0 → 114.5 GPU-s).

Direction B — Five Data-Movement Upgrades in Production Clover (8 × RTX 3090)

Measured on real 92-layer Kimi K3 traces (43,240 layer calls = 470 passes), standalone RTX 3090 CUDA benchmarks (bench_dm_cycles_gpu.cu), and live 93-layer production server runs (docs/clover-data-movement-direction-b-context.md).
Study & Mechanism Before (Baseline Policy 1 / Shipped Kernel) After (Production Clover Direction B) Measured Impact on 8 × RTX 3090
1. Red-Blue Pebble Game (Hong & Kung, STOC 1981)
Clean-Input R4 Host-Shadow Admission		 Exclusive swap: HostCache hits removed on H2D; every CardPool eviction copied 17.55 MB back over PCIe D2H (R2_WB = 54,132..200,717). Parallel NVMe pread directly into HostCache shadow slots in libsupply.so + sc_worth = 0 when resident in HostCache. written_back_R2 = 0 on cold NVMe reads and warm H2D hits; 25,533 R4 clean drops saving 448.0 GB of redundant PCIe D2H traffic (1.95× faster PCIe wall-clock).
2. SpecMD (Hoang et al., arXiv:2602.03921)
Policy 3 Least-Stale (LS) + Hit-First + Cross-Layer Lookahead		 Heat-48 pinned Pass-0 prefill experts and evicted upcoming layers ($l_e > l_{\text{cur}}$), causing 9.35%–24.53% pass-collision misses; vram_mask==2 charged to cold budget. 3-tier Least-Stale (LS) eviction in libslotcache.so + two-pass Hit-First in libsupply.so + free vram_mask==2 + Layer $L+1$ lookahead & async H2D prefetch. Pass-collision misses cut by 11.8×–26.7× (24.53% → 0.92%); live server dynamic CardPool hit rate reached 86.09%–86.51% and overall VRAM hit rate reached 95.22%–95.29%.
3. FlashAttention-1 & 2 (Dao et al., 2022/2023)
Warp-Coalesced Register Online-Softmax + Split-KV MLA		 mla_attention_pos materialized sc[count] in dynamic shared memory with 3 block-wide barriers and 1 thread/feature for V accumulation. mla_attention_pos_fa2_part + mla_splitkv_combine: 1 key/warp coalesced float4 loads, register o0..o3, 0 B dynamic smem, Split-KV logsumexp combine. 2.57×–3.40× faster at N_q = 1 and 3.81×–6.84× faster at N_q = 4 (4,295.4 → 646.8 μs at KV = 4,096), max_abs_diff ≤ 1.12e-7.
4. Eyeriss v1 (Chen et al., ISCA 2016 / JSSC 2017)
4-Tier Storage & Energy Movement Ledger		 No per-tier byte/energy accounting across GPU SRAM ($1\times$), VRAM ($2\times$), Pinned Host RAM ($6\times$), and NVMe ($200\times$). Live k3_full93_dm_stats ledger in libk3_gpu_experts.so exposed via /api/health and k3_data_movement_ledger.py. Eyeriss weighted movement cost per expert request dropped from 54.205 to 7.731–8.998 across the full benchmark runs (a 6.0×–7.0× reduction).
5. Eyeriss v2 (Chen et al., IEEE JETCAS 2019)
Adaptive Multi-Token Broadcast Coalescing		 Independent per-token cold expert selection in multi-token windows fetched 920 dynamic experts/pass (1.42× token reuse/expert). coalesce_cold_broadcast prioritizes shared cold experts demanded by $\ge 2$ frontier tokens (vram_mask = 3) within k_dyn_max. Cold dynamic expert fetches per 93-layer pass dropped by 80.0% (920 → 184), token reuse per cold expert rose 1.42× → 3.38×, and 93-layer GPU speed reached 148.5 tok/s (112.1 ms/layer).

Where we started, and where it is now

We started from Fareed Khan’s kimi-k3-in-c (Apache-2.0) on a single CPU workstation (AMD Ryzen 9 7950X3D, 124 GB RAM, dual NVMe RAID1), optimized the 93-layer CPU reference chain bit-identically, and then built the unified 7-layer Clover architecture on 8 × RTX 3090 GPUs.

Credit

Clover builds directly on the open weights, architectures, and published research of the teams below:

  • Moonshot AI — Kimi K3 (moonshotai/Kimi-K3). The 2.78-trillion-parameter 93-layer Mixture-of-Experts model (69 KDA + 24 MLA attention layers, 896 routed experts per layer, d = 7,168), the 27-layer MoonViT3d + PatchMergerMLPV2 vision tower, and the 163,840-token tiktoken.model vocabulary. The embedding table, output head, final normalization, vision weights, and tokenizer files are read from the original open weights under their own names.
  • Jiaru Zou, Yunzhe Qi, Sirui Chen, Federico Bianchi, Shang Zhu, Pan Lu, Jingrui He, and James Zou (Stanford University, Together AI, UIUC, Meta) — HybridAgent (arXiv:2610.18861, togethercomputer/HybridAgent). Hybrid Reasoning Agents: LLM Agents that Think in Latent Space, Act through Text. We use their HybridAgent-8B-Agentic model, HybridLink continuous <latent> reasoning mechanism, and <search> / <python> agent architecture, and extend the HybridLink design to Kimi K3’s 7,168-dimensional hidden states (K3NativeHybridLink).
  • Hermann Kumbong, Ishan S. Khare, Iddah Mlauzi, Andrew Woen, Charles Ding, E. Kelly Buchanan, Simran Arora, Azalia Mirhoseini, and Christopher Ré (Hazy Research, Stanford University) — Next-Concept Modeling (arXiv:2610.14162, HazyResearch/ncm, MIT License). Next-Concept Modeling: Fast, Parallel Coarse-to-Fine Text Generation. We adapt their 11-level multiscale residual VQ-VAE tokenizer and coarse-to-fine NextConceptTransformer to Kimi K3’s 163,840-token vocabulary and 7,168-dimensional geometry.
  • Domenico Benfenati and Antonio Maria Rinaldi (University of Naples Federico II) — Ontology-Guided Neuro-Symbolic GraphRAG (doi:10.1007/s00521-026-12495-0, CosmoIknosLab/ontology-guided-graphrag, MIT License). Ontology-Guided Neuro-Symbolic GraphRAG for Grounded Query Answering (Neural Computing and Applications, 2026). We build on their loosely-coupled neuro-symbolic design keeping deterministic ontology graph materialisation, Horn-rule inference, and edge provenance separate from neural generation, along with the six retrieval and verifier enhancements documented in clover-ontology-graphrag-research-context.md.
  • Fareed Khan — kimi-k3-in-c (Apache-2.0). The C engine that showed Kimi K3 could be run from C on one workstation, where our CPU measurements started. Five of its tokenizer headers are included unmodified at commit a2ad8e5 with its licence and notice.
  • Inferact — Kimi-K3-DSpark. The 5-layer dense MLA draft model used for speculative decoding on the CPU workstation.
