A 2.78-trillion-parameter model, written as its equation

We took Kimi K3, wrote down what it computes as one mathematical expression, and ran that directly as a single C file. It produces the same answer as an independent implementation of the same model on every prompt tested, in under a third of the time, on one rented CPU machine with no GPU.

It is also not fast enough to talk to — about six seconds per word once it starts writing. That part is on this page too, with the numbers, because a page that only showed the good result would not be worth reading.

The code The 34 prompts, and what it writes

What we actually did

A large language model is usually met as a program you run. We wanted to know what it is, separately from how anyone happens to have implemented it. So we wrote the model out as mathematics first, and only then turned that into code.

1. Take the model apart, one kernel at a time
Forty-two numbered stages across two layers, then a walk over all ninety-three. Each stage establishes one operation and what it does to real values, checked against the running model rather than reasoned about.
2. State the whole thing once, as one expression
Ten primitive operators, two kinds of attention block, two kinds of MLP block, and one composed expression for the whole model. Nothing left as prose. Supply the token ids, evaluate the expression, and you get the token the model emits.
3. Execute the document and see whether it is true
The equation was transcribed into a program and run against the original engine's own internal values. 79,742,816 float32 values identical, zero mismatches. That is what turned it from a description into a specification.
4. Build the real implementation from the equation, not from anyone's code
One C file, about 2,500 lines, no dependency beyond libc, libm and OpenMP. Every change from that point had to reproduce one checksum, or it did not count.

Writing it down is what found the mistakes

Executing the document rather than admiring it exposed four defects in our own mathematics. Each one is recorded where it was found:

The int8 projection had eight accumulators where the model has sixteen
Mathematically the same sum; numerically a different one. As first written it reproduced 2,012 of 12,288 values.
A weight was stored at width 128 with only 96 entries used
Correct arithmetic, unstated shape. Implementing from the document alone gave a shape error.
One operator never said whether its multiply and add were fused
The obvious translation is a fused multiply-add, which rounds once. The model rounds twice. The build carries -ffp-contract=off for that reason.
The expert weighting said divide where the model multiplies by a reciprocal
Found by reading the finished code back against the document. Both forms were built into one binary and compared: 92% of the output values differ, though the emitted word does not change — which is exactly why it survived unnoticed.

The order of operations is not a formatting detail in this work. Three separate times, a regrouping that is correct in ordinary algebra dropped the match to between 74% and 80%.

What the results showed

The test is deliberately blunt. Give two independently written programs the same 34 prompts, the same 1.5 TB of weights, the same machine, on the same day, and see whether they agree and how long they take. The other program is kimi-k3-in-c, a separate C implementation that shares no code with ours.

34 of 34 answers identical
Not similar — the same token id every time. The capital of France is Paris; the chemical symbol for gold is Au; the largest planet is Jupiter. Asked in English, French and German, the Paris question returns the identical token id in all three.
394.94 seconds against 1344.23 seconds
Across all 34 prompts. A ratio of 3.40, and between 3.17 and 3.57 on any individual prompt.
One checksum held through every optimisation
23d162dcefb18211a7540ef12948f1eb. A faster result that does not reproduce those bytes is not a result. This caught a change that looked like a 38% win and was silently wrong.
Routing turned out to be predictable
Which experts a position needs is a pure function of the words before it — measured 644 agreements out of 644, with a control that fails as it should. So for a prompt seen before, the weights the next layer needs can be fetched while the current layer is still computing. That took a five-token prompt from 8.75 to 7.25 seconds and the disks from 80% to 99% busy.

Where the gap actually comes from

Both programs read exactly the same 99.72 GB of expert weights, so neither is doing less arithmetic. Of the 14.79-second gap on the first prompt, 5.73 seconds is simply the other program re-reading the 54 GB trunk from disk on every run while ours keeps it in memory. That is a configuration choice, not a clever one. The rest is overlap: ours keeps the disks busy while it computes.

We also measured the disks directly, using our own access pattern: they top out at 14.6 GB/s, and the run is already reading at 13.8. There is about 6% left in the hardware, not 60%.

Setting it up and running it

Nothing here ships the model. The checkpoint is Kimi's and stays theirs, and the packed trunk is built by the upstream engine's own tools. What this repository holds is the program, the index builders, the prompts and the correctness gate.

What you need first
The released Kimi K3 checkpoint (the .safetensors shards, about 1.5 TB) and the packed trunk built by the upstream engine's tools/pack_trunk.py and tools/int8_trunk.py. Nothing in clover-k3 reproduces either.
Point it at them
Every path lives in one file, config.env, and nothing else in the folder names a location. The program refuses to start if the index and trunk paths are unset rather than guessing a default, because a silently wrong index produces a confident wrong number.
Build
./build.sh — this also generates the tensor index. The prompt length is a compile-time constant, so a build is for one length: NPOS=64 ./build.sh. Everything generated lands in build/.
Check it before believing it
./gate.sh must print 23d162dcefb18211a7540ef12948f1eb. A timing from a build that has not passed the gate means nothing.
Run a prompt
Set the token ids with K3_IDS and run build/clover-k3. Thread pinning is not optional on a two-chiplet processor — unpinned runs vary by seconds, and every measurement taken before we adopted it had to be redone.

There are 33 switches. The ones worth knowing are the reader-thread count, the prefetch mode, and the routing cache that enables reading a layer ahead. The rest are instrumentation and are off by default; turning all of it off was measured and changes nothing.

The machine, and what it really costs

One rented machine. No GPU, no cluster, nothing exotic.

Processor

AMD Ryzen 9 7950X3D. 16 cores, 32 threads. We measured that 16 compute threads is the right number — using all 32 for arithmetic makes it slower, because the paired threads share the cache the kernel depends on.

Memory

124 GB installed. Our run peaks at 58.05 GB resident; the other implementation peaks at 51.09 GB for one token and 95.5 GB while generating. None of these is a small-memory configuration.

Storage

Two NVMe drives in RAID1. 1.5 TB for the checkpoint plus 51 GB for the trunk, and the array is 91% full holding them. Every run reads 99.86 GB back off the disks.

The honest summary of the requirement is that storage is the entry fee and memory is the working cost. You cannot start without roughly 1.6 TB of fast local disk. Once started, the thing that decides your speed is how much of the model you can keep resident and how well you overlap reading the rest with computing.

The upstream engine is designed to run in far less memory than this, and can. We did not ask it to here; both programs were given the machine as it is.

Is this interactive enough for real work?

No. Not yet, and not close.

It is worth being exact about why, because the headline numbers on this page are about reading a prompt, not about writing an answer. Those are different costs, and only the first one is fast.

The 34-prompt comparison is one token per prompt
Both programs were asked to read a prompt and produce the single next word. The 7.23 seconds in the table is a whole prompt read from cold, which is the part we set out to understand — not a sentence produced.
It does write sentences, at about six seconds a word
Each new word reuses the state the previous one left, so only the new position is computed. Measured steady state: 5.1 s per word after a five-word prompt, 6.6 s after a ten-word one. The reuse is checked against recomputing everything from scratch and produces the identical words, 2.34x faster. For reference the upstream engine measured 23.71 s per token over 8 tokens and 12.42 s over 128 on this same machine.
Fourteen words took a hundred seconds
“In 1969 the first humans landed on the” continued to “moon. The Apollo 11 mission was a monumental achievement in human history” — 14 tokens in 101.3 seconds. A 128-word answer would be around thirteen minutes.

So for day-to-day work — a chat window, a coding assistant, anything with a person waiting — this is not usable, and no amount of tuning at the margin changes that. Six seconds a word is not a slow version of interactive. It is a different activity.

What it is genuinely good for right now

Work where the answer matters more than the wait, and where the alternative is not having the model at all: running a frontier-scale model on hardware you control rather than someone's API, checking that an implementation is exactly correct, or batch work left to run. It also establishes the thing the speed rests on — that the model is understood well enough to be written down and checked value by value.

The direction that could change the answer is placement rather than tuning: keeping the most-used part of the model on a GPU while the rest stays on disk. That has not been measured, and until it is, it is an idea and not a result.

What this does not show

Stated plainly, because a result that hides its edges is not evidence.

  • One token per prompt in the comparison. The 34-prompt table asked both programs for the next token only. Generation was measured on clover-k3 alone, at different prompts and lengths from the engine's figures, so the two are separate observations rather than a ratio.
  • Not a comparison against the official runtime, or a GPU. It is one CPU implementation against another CPU implementation of the same checkpoint.
  • Thirty-four prompts, mostly short and mostly English. The longest is 24 tokens. Nothing here speaks to long context.
  • The trunk-caching difference is quantified but not controlled for. A version of the test with both programs cold, or both warm, has not been run.
  • Single runs, not repeated trials. Run-to-run spread on this machine is around 0.1 s within a session and up to 2 s across sessions — small against a threefold gap, but not zero.
  • One machine. Every number on this page comes from the same box.
