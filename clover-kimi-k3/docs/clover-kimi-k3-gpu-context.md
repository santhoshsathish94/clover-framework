# clover-kimi-k3 GPU context

The dated record of the GPU work, the way `clover-kimi-k3-cpu-context.md` is the record of the CPU engine. Each entry says what was run, on what, what was observed and what it does not cover. Written after every cycle.

## Direction (the creator's, 2026-10-20)

Run the layers on the GPUs with everything a layer needs held in video memory (the layer's trunk files and, for layer 1, all 896 experts), and see how much faster than the CPU engine it is. Start with layer 0 and layer 1. Go one step at a time. The pipeline idea (one layer's experts per card, the next layer's prefetched) was recorded earlier as an idea, not a decision, and is not what this first step tests.

## Where this runs

Rented server `gpu` (141.101.132.38, user `usergpu`, passwordless sudo by the creator's choice): 8 x RTX 3090 24 GiB (23.6 GiB usable as reported by CUDA), 2 x Xeon Gold 6248R (96 threads), 376 GiB RAM, one NVMe (3.25 GB/s sequential best), driver 580.178.04, CUDA toolkit 12.6, `gcc` 13.3. Rented from 20.10.26 00:06 to 27.10.26 01:20. NVLink only between pairs 0-2, 1-3, 4-6, 5-7. All cards on CPU socket 0. Details and measurements are in `clover-kimi-k3-cpu-context.md` (entries of 2026-10-20) because they were taken before this file existed.

## How a GPU result is judged (first candidate, not final)

The CPU engine is bit-identical to the pod's recorded chain end to end. A GPU layer is judged against the CPU engine's rows for the same input, saved by `PF_SAVE_ROWS=base` with `PF_LAST_LAYER=L` (`base.embed`, `base.layer0`, `base.layerL`). The report gives bit-identical share, maximum absolute difference, relative RMS difference and the lowest cosine of a position. Matrix sums on the GPU run in a different order and (for the experts) in float instead of double, so bit-identity is not expected from the matrix products; it is not claimed. No tolerance is fixed yet; the creator sets it.

- Against the CPU engine's output (1000 x 7168 values): bit-identical 1.18%, no non-finite values, maximum absolute difference 1.58e-06, relative RMS difference 2.51e-06, lowest cosine of a position 1.000000000, worst position 536 (relative RMS 3.24e-06). One input, one prompt, layer 0 only; not compared with the pod directly (the CPU engine is the reference).

Loading the experts took 11.2 s (1.40 GB/s) while the download was writing to the same disk; the trunk 0.83 s.

- Time on card 0, three runs, layer 1 for 1000 tokens: 503.1, 487.0 and 488.7 ms. Stages in the last run: aggregate and norm 0.7, q/k/v matrices 39.2, convolution and l2 3.8, decay and beta 5.4, recurrence 13.6, gate and output matrix 28.3, residual aggregate and norm 0.8, router with top 16 and the lists on the host 99.1, latent with the experts (gate, up, down) 271.5, mix and latent norm and back projection 4.4, shared expert and sum 21.9 ms. Not included: loading weights, copying the input in and the result out. The CPU engine's layer 1 on the same server took 6,019 to 6,261 ms in three runs (download running). About 12 to 13 times faster than those runs.

## 2026-10-20 — layer 0 alone: where its 205 ms go

Question (the creator): why does layer 0 take that long, where is the time spent. Measured with NVIDIA's profilers on the server, card 0, the 1000-token window, three runs under `nsys` (per-kernel times), one kernel under `ncu` (why it is as fast as it is), and cuBLAS on the same shapes as a ceiling (`src/code/gpu/probes/sgemm-ceiling.cu`).

Per run, summed over kernels (205.8 ms, the same as the 205 ms the program timed): the 8-bit matrix kernel `gemm_i8` 177.1 ms (86.0%, 11 launches); `recurrence` 13.85 ms (6.7%); `dense_activation` 6.9 ms (3.4%); `conv_silu` 2.6 ms; `decay_transform` 1.7 ms; `l2_heads` 1.2 ms; `normalize_rows` 1.0 ms; `gate_mul` 0.84 ms; `aggregate` 0.52 ms; the rest under 0.2 ms. So it is the matrix product: 2.35 TFLOP of float work in 177 ms is about 13.3 TFLOP/s. The layer's weights are 1.44 GB; read once at the card's 936 GB/s that is 1.5 ms, so the matrices are not waiting for memory: `ncu` on the dense gate launch shows DRAM throughput 5.6% (51 GB/s).

What limits the matrix kernel (`ncu`, dense gate launch, 33792 x 7168 for 1000 tokens; `ncu` fixes the clock at base, so its 43.3 ms is not comparable to the 39 ms of the run): memory pipes busy 85% (L1/TEX throughput 85.9%), the FMA pipe 40%, issue slots busy 54%, IPC 2.16 of 4; occupancy 33% because each thread uses 127 registers (2 blocks of 256 threads per SM); L1 hit rate 26%; the weight loads use 18.7 of every 32 bytes of a sector (each thread reads 4 bytes from its own row), 38% of the sectors fetched are excess. In words: the kernel spends its time moving data through shared memory and the L1 (16 shared-memory loads for every 64 multiply-adds), not on the multiply-adds, and has too few warps to hide the waits.

What the card itself does on these shapes, cuBLAS with float weights (no 8-bit decode): 19.0 to 19.3 TFLOP/s on the dense gate and the q/k/v shape, 17.7 on the dense down shape (25.2, 9.2 and 27.3 ms). The card's theoretical peak is 35.6 TFLOP/s at 1695 MHz, but under load the card ran at 1455 MHz, 323 W of the 350 W limit, throttle reason "software power cap" (sampled once, in the cuBLAS run): at that clock the peak is about 30.5 TFLOP/s. So NVIDIA's float kernel reaches about 62% of that peak, and ours 43%. Our kernel is about 1.5 times slower than cuBLAS on the same shape (the dense gate or up launch: 39 ms against 25 ms). With cuBLAS-level float kernels the matrix part of layer 0 would be about 120 ms instead of 177 ms, and layer 0 about 150 ms instead of 205 ms. TF32 tensor cores did 33 to 37 TFLOP/s in the same probe, but they round the inputs to 10 bits of mantissa, so the numbers are not the float product's; shown only as a speed reference, not used.

What the numbers do not say: why exactly the kernel is below cuBLAS (the candidates below are from the counters, none has been tried), and whether the layer's other 14% can be reduced (the recurrence is 96 blocks in sequence over 1000 positions; the double-precision exp and tanh in `dense_activation` cost 6.9 ms because double runs at 1/64 of float on this card).

Candidates, untested, for the creator to choose from: (1) rewrite the matrix kernel for fewer shared-memory instructions per multiply-add (vector shared loads, larger register tile, loads of the 8-bit weights staged by `cp.async` in full sectors, 2 to 3 blocks per SM) toward the cuBLAS figure; (2) integer tensor cores: the weights are exact 8-bit integers, so the activations could be cut into 8-bit planes with one scale per token and the product taken exactly in integers; the card does far more integer operations per second than float ones (not measured here), but the result would differ from the float product by the rounding of the activations to the planes' width, to be measured against the CPU engine before any claim; (3) leave the matrix as it is and look at layer 1's router (99 ms) and expert kernel (271 ms) first, where the time is larger in absolute terms.

## 2026-10-20 — three speed experiments run at the same time, one per card

Direction (the creator): do all three candidates from the entry above, not one after the other, on three cards. Card 1: a rewritten matrix kernel. Card 2: the integer tensor cores. Card 3: layer 1's router and expert kernel. Card 0: the unchanged layer 1 as a control. First each on its own as a microbenchmark or flagged variant, then the four variants together inside the real layers (cards 0 to 3 again). All on the recorded 1000-token prompt, real weights, the CPU engine's rows as input and reference. The runs overlapped in time but not on a card; card clocks and power were not sampled in these runs.

**A. Matrix kernel v2** (`gemm_i8_v2` in `kernels.cuh`: 32 columns of k per step so each weight row is read in whole 32-byte sectors, the next step's loads held in registers, shared memory read in 16-byte pieces, 4 shared loads per 64 multiply-adds instead of 16). Microbenchmark on the real trunk-0 weights (`probes/gemm-simt-bench.cu`), v1 against v2: dense gate or up 34.68 -> 27.94 ms (13.97 -> 17.34 TFLOP/s), dense down 38.30 -> 30.52 ms (12.65 -> 15.87), q/k/v 13.07 -> 10.62 ms (13.48 -> 16.58); 1.23 to 1.25 times faster; the outputs are bit-identical to v1 (100.0000% of the values, maximum difference 0), as designed (same order of additions per output). cuBLAS float was 17.7 to 19.3 TFLOP/s on the same shapes earlier, so v2 is at about 90% of it. v2 is now the default. In layer 0: 205 ms -> 173.1, 172.1 and 173.8 ms (runs 3 to 5), the same bits as before (bit-identical 1.21%, relative RMS difference 2.48e-06, same worst position 194).

**B. Integer tensor cores** (`probes/gemm-imma-bench.cu`; in the layers behind `-DINT8_PLANES`, cuBLAS int8 product). Each token's activations scaled by the token's largest value and cut into signed 8-bit digits; one exact integer product per digit; digits recombined in double; row scale applied. Microbenchmark against the float kernel v1: 3 digits (23 bits) 7.32, 6.89 and 3.22 ms for the three shapes (4.77, 5.67 and 4.06 times faster; the integer product itself ran at 188 to 234 TOPS), difference from the float result: relative RMS 3.2e-07, 1.9e-06 (dense down, synthetic random inputs because the real input to that matrix was not saved), 3.9e-07. 2 digits (15 bits) were 5.8 to 8.5 times faster but differ by 1.2e-05 to 3.7e-05 relative RMS, which is 10 to 100 times the float kernel's own noise: not used. In layer 0 with 3 digits for every matrix: 205 ms -> 64.5, 67.0 and 66.7 ms (runs 3 to 5), about 3.1 times faster; against the CPU engine's layer 0: relative RMS difference 8.99e-07 (the float kernels: 2.48e-06), maximum absolute difference 1.49e-07 (1.58e-06), bit-identical 3.31% (1.21%), lowest cosine 1.000000000, worst position 252 (relative RMS 1.52e-06). The integer path is closer to the CPU engine than the float path is in layer 0. In layer 1 (below) it is not: see C.

**C. Layer 1's router and experts** (`-DFAST_ROUTER`, `-DEXPERT_V2` in `layer1.cu`). Router: the scores for all 896 experts from a float cuBLAS product, then the exact double score only for the experts whose approximate choice is within 1e-3 of the 16th, and the selection and weights made from the exact values. Router stage 99.3 -> 10.6 to 11.5 ms (the first run of a process takes more, 62 ms, for starting cuBLAS); the same 16 experts in the same order for 1000 of 1000 tokens, bit-identical weights for 1000 of 1000 tokens, checked in the same run against the all-double router on the same input. Expert kernel v2 (each thread holds 4 rows by 4 tokens so one 16-byte shared read feeds 8 multiply-adds): the gate, up and down products 270 -> 177 to 180 ms, about 1.5 times faster, about 6 TFLOP/s; the layer's output is bit-identical to the unchanged layer's (hash f5c6b6c3bc2e4d9c on card 0's control run and on card 3). Layer 1 with the fast router, expert v2 and matrix v2: 488 -> 294.3, 292.2 and 293.1 ms (runs 3 to 5), 1.67 times faster, same bits as before (bit-identical 2.03% against the CPU engine, relative RMS difference 1.55e-06, maximum absolute difference 8.34e-07, worst position 373).

**All four together in layer 1** (fast router, expert v2, integer planes for the trunk matrices): 234.9, 238.4 and 234.1 ms (runs 3 to 5), 2.1 times faster than 488 ms; the routing is still identical to the all-double router's on 1000 of 1000 tokens. Against the CPU engine: relative RMS difference 2.7e-06 (the float path: 1.55e-06), maximum absolute difference 5.96e-07 (8.34e-07), bit-identical 1.21%, lowest cosine 1.000000000, worst position 68 (relative RMS 5.34e-06). So with the integer planes layer 1 is a little further from the CPU engine in the relative RMS and its worst position (about 1.7 times), though its largest single difference is smaller; layer 0 went the other way. Not understood: which matrix in layer 1 adds the difference (the experts stay in float; the latent projection, the back projection, the shared expert and the attention matrices use the planes).

**Where layer 1 is now:** 234 ms, of which the experts are 175 ms (75%), the recurrence 14.6 ms, the router stage 11 ms, the q/k/v matrices 10 ms, the gate and output matrix 7 ms. Against the CPU engine on the same server (layer 0 1.9 to 2.6 s, layer 1 6.0 to 6.3 s, download running then) layer 0 is about 30 times faster and layer 1 about 26 times faster with all changes on; with the bit-identical changes only (matrix v2, router, expert v2) layer 0 is about 12 times and layer 1 about 21 times faster.

Not covered: other prompts (the integer digits are scaled by each token's largest value, so a token with one huge value among small ones loses precision in the small ones; only this prompt's tokens were seen); other cards' clocks and power; the tolerance the creator wants (still not set); loading time of the weights (not in these figures); layers 2 and onward; any decode step. Next candidates, not started: the expert kernel (75% of layer 1 now: integer-style tensor cores do not apply as directly since the expert weights are 4-bit codes mapped to 66 values, so a decode-and-multiply on tensor cores in half precision or an int8 re-coding of the 4-bit values would be new work); the recurrence (14 ms, sequential over positions); experts for several layers across several cards.

## 2026-10-20 — supplying one layer's experts to the cards (the cycle's two legs, measured)

Question (the creator): the full run as planned, 8 cards, one layer at a time, trunk fixed, the experts of the next layer for a card brought in while the other cards work; and "are you forgetting we have 384 GB of RAM". Before building the 93-layer run, the cost of moving one layer's experts (896 experts, 15.72 GB) was measured with `probes/expert-supply.cu`: from the NVMe with O_DIRECT, from the page cache, and from pinned host memory over the bus, with one card and with eight cards at the same time. The layer-1 experts used in the earlier runs were loaded to the card once, before the timed runs (all 896 at once, 11 to 12.5 s each time); they were not fetched during the layer.

Answer to the RAM question: it is counted, and it helps one leg. Right now 364 GiB of the 376 GiB is page cache (the dataset's most recently written files). One layer's experts are 14.64 GiB, so RAM holds about 25 of the 92 layers; the other 67 layers' experts have to come from the one NVMe.

Measured, one run each:
- NVMe, O_DIRECT, one card, 8 reader threads: 5.16 s for one layer (3.05 GB/s). Eight cards at the same time, each a different layer: 39.58 s for 8 layers, 3.18 GB/s in all, 4.95 s per layer. The disk gives about 3.1 GB/s however many cards ask.
- RAM to card (pinned memory, 2 reader threads per card): one card 2.10 s for one layer (7.48 GB/s). Eight cards at the same time: 7.57 s for 8 layers, 16.6 GB/s in all, 0.95 s per layer on average, about 2.1 GB/s per card. All eight cards sit on CPU socket 0, so they share the host side of the bus.
- Buffered reads of a file that is in the page cache, one card: 2.18 s (7.2 GB/s), the same as the bus alone.

What it means for the cycle (arithmetic from the measurements and the layer times in the earlier entry; not a measurement of the cycle): a layer's compute for the 1000-token window is 0.23 s (all speed flags) to 0.29 s, but supplying its experts costs 0.95 s per layer at best (from RAM, eight cards fed together) and 4.95 s from the disk. So the supply, not the card, sets the speed of one window going through the layers: about 25 x 0.95 + 67 x 4.95 = 355 s for the 92 layers (the 25 layers in RAM first, the rest from the NVMe), against 92 x 0.23 = 21 s of compute. The CPU engine took 297 s for the same 1000 tokens on the workstation (two NVMe in RAID 1). If every layer were in RAM it would be about 92 x 0.95 = 87 s. The RAM does not remove the disk problem; it covers 25 of 92 layers.

What would change it (each not tried): more tokens per layer load (the 15.7 GB is paid once per layer however many tokens use it; a window of N tokens needs about 0.25 x N/1000 s of compute per layer, so the compute and the 0.95 s from-RAM supply meet near 4000 tokens, but the buffers for 4000 tokens do not fit beside the experts and a trunk share on a 24 GiB card); keeping some layers' experts in the cards' memory for good (8 x 23.6 GiB is about 188 GiB, room for at most about 11 layers' experts with nothing else); a second drive or a faster read path; a smaller expert format. Not covered: pinning 360 GiB (the shell's locked-memory limit is 47 GiB, root can raise it), the real cycle with compute and copies overlapping, and the speed of the MLA layers (not written for the GPU).
