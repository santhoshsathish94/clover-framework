# clover-kimi-k3 GPU context

The dated record of the GPU work, the way `clover-kimi-k3-cpu-context.md` is the record of the CPU engine. Each entry says what was run, on what, what was observed and what it does not cover. Written after every cycle.

## Direction (the creator's, 2026-10-20)

Run the layers on the GPUs with everything a layer needs held in video memory (the layer's trunk files and, for layer 1, all 896 experts), and see how much faster than the CPU engine it is. Start with layer 0 and layer 1. Go one step at a time. The pipeline idea (one layer's experts per card, the next layer's prefetched) was recorded earlier as an idea, not a decision, and is not what this first step tests.

## Where this runs

Rented server `gpu` (141.101.132.38, user `usergpu`, passwordless sudo by the creator's choice): 8 x RTX 3090 24 GiB (23.6 GiB usable as reported by CUDA), 2 x Xeon Gold 6248R (96 threads), 376 GiB RAM, one NVMe (3.25 GB/s sequential best), driver 580.178.04, CUDA toolkit 12.6, `gcc` 13.3. Rented from 20.10.26 00:06 to 27.10.26 01:20. NVLink only between pairs 0-2, 1-3, 4-6, 5-7. All cards on CPU socket 0. Details and measurements are in `clover-kimi-k3-cpu-context.md` (entries of 2026-10-20) because they were taken before this file existed.

## How a GPU result is judged (first candidate, not final)

The CPU engine is bit-identical to the pod's recorded chain end to end. A GPU layer is judged against the CPU engine's rows for the same input, saved by `PF_SAVE_ROWS=base` with `PF_LAST_LAYER=L` (`base.embed`, `base.layer0`, `base.layerL`). The report gives bit-identical share, maximum absolute difference, relative RMS difference and the lowest cosine of a position. Matrix sums on the GPU run in a different order and (for the experts) in float instead of double, so bit-identity is not expected from the matrix products; it is not claimed. No tolerance is fixed yet; the creator sets it.

## 2026-10-20 — layer 0 alone: where its 205 ms go

Question (the creator): why does layer 0 take that long, where is the time spent. Measured with NVIDIA's profilers on the server, card 0, the 1000-token window, three runs under `nsys` (per-kernel times), one kernel under `ncu` (why it is as fast as it is), and cuBLAS on the same shapes as a ceiling (`src/code/gpu/probes/sgemm-ceiling.cu`).

Per run, summed over kernels (205.8 ms, the same as the 205 ms the program timed): the 8-bit matrix kernel `gemm_i8` 177.1 ms (86.0%, 11 launches); `recurrence` 13.85 ms (6.7%); `dense_activation` 6.9 ms (3.4%); `conv_silu` 2.6 ms; `decay_transform` 1.7 ms; `l2_heads` 1.2 ms; `normalize_rows` 1.0 ms; `gate_mul` 0.84 ms; `aggregate` 0.52 ms; the rest under 0.2 ms. So it is the matrix product: 2.35 TFLOP of float work in 177 ms is about 13.3 TFLOP/s. The layer's weights are 1.44 GB; read once at the card's 936 GB/s that is 1.5 ms, so the matrices are not waiting for memory: `ncu` on the dense gate launch shows DRAM throughput 5.6% (51 GB/s).

What limits the matrix kernel (`ncu`, dense gate launch, 33792 x 7168 for 1000 tokens; `ncu` fixes the clock at base, so its 43.3 ms is not comparable to the 39 ms of the run): memory pipes busy 85% (L1/TEX throughput 85.9%), the FMA pipe 40%, issue slots busy 54%, IPC 2.16 of 4; occupancy 33% because each thread uses 127 registers (2 blocks of 256 threads per SM); L1 hit rate 26%; the weight loads use 18.7 of every 32 bytes of a sector (each thread reads 4 bytes from its own row), 38% of the sectors fetched are excess. In words: the kernel spends its time moving data through shared memory and the L1 (16 shared-memory loads for every 64 multiply-adds), not on the multiply-adds, and has too few warps to hide the waits.

What the card itself does on these shapes, cuBLAS with float weights (no 8-bit decode): 19.0 to 19.3 TFLOP/s on the dense gate and the q/k/v shape, 17.7 on the dense down shape (25.2, 9.2 and 27.3 ms). The card's theoretical peak is 35.6 TFLOP/s at 1695 MHz, but under load the card ran at 1455 MHz, 323 W of the 350 W limit, throttle reason "software power cap" (sampled once, in the cuBLAS run): at that clock the peak is about 30.5 TFLOP/s. So NVIDIA's float kernel reaches about 62% of that peak, and ours 43%. Our kernel is about 1.5 times slower than cuBLAS on the same shape (the dense gate or up launch: 39 ms against 25 ms). With cuBLAS-level float kernels the matrix part of layer 0 would be about 120 ms instead of 177 ms, and layer 0 about 150 ms instead of 205 ms. TF32 tensor cores did 33 to 37 TFLOP/s in the same probe, but they round the inputs to 10 bits of mantissa, so the numbers are not the float product's; shown only as a speed reference, not used.

What the numbers do not say: why exactly the kernel is below cuBLAS (the candidates below are from the counters, none has been tried), and whether the layer's other 14% can be reduced (the recurrence is 96 blocks in sequence over 1000 positions; the double-precision exp and tanh in `dense_activation` cost 6.9 ms because double runs at 1/64 of float on this card).

Candidates, untested, for the creator to choose from: (1) rewrite the matrix kernel for fewer shared-memory instructions per multiply-add (vector shared loads, larger register tile, loads of the 8-bit weights staged by `cp.async` in full sectors, 2 to 3 blocks per SM) toward the cuBLAS figure; (2) integer tensor cores: the weights are exact 8-bit integers, so the activations could be cut into 8-bit planes with one scale per token and the product taken exactly in integers; the card does far more integer operations per second than float ones (not measured here), but the result would differ from the float product by the rounding of the activations to the planes' width, to be measured against the CPU engine before any claim; (3) leave the matrix as it is and look at layer 1's router (99 ms) and expert kernel (271 ms) first, where the time is larger in absolute terms.

What would change it (each not tried): more tokens per layer load (the 15.7 GB is paid once per layer however many tokens use it; a window of N tokens needs about 0.25 x N/1000 s of compute per layer, so the compute and the 0.95 s from-RAM supply meet near 4000 tokens, but the buffers for 4000 tokens do not fit beside the experts and a trunk share on a 24 GiB card); keeping some layers' experts in the cards' memory for good (8 x 23.6 GiB is about 188 GiB, room for at most about 11 layers' experts with nothing else); a second drive or a faster read path; a smaller expert format. Not covered: pinning 360 GiB (the shell's locked-memory limit is 47 GiB, root can raise it), the real cycle with compute and copies overlapping, and the speed of the MLA layers (not written for the GPU).

## 2026-10-20 — steps 2 and 3: the cycle's data path on eight cards with no computing, and the budget

Step 2 program: `probes/cycle-io.cu` (layers go from the disk through pinned RAM slots, one reader thread pool and one loader thread per card, to the card that owns the layer, layer L on card L mod 8; a stand-in takes a fixed time per layer in layer order and only then frees that card's expert buffer; it measures what the stand-in waits for). One run of each setting, nothing else running, stand-in 250 ms per layer (about what one 1000-token window needs per layer on a card with the speed options on).

- **Disk to RAM to cards, layers 1 to 16, 8 RAM slots, 2 reader threads, reads through the page cache:** 157.9 s in all, 9.53 s per layer after the first, 1.59 GB/s; the stand-in waited for experts 139 s of the 143 s and computed 3% of the time. Reading layers 3 and 4 together took 18 to 19 s for 31 GB (1.6 GB/s), against 2.9 GB/s for the disk alone in step 1.
- **The same with O_DIRECT reads:** 79.4 s, 4.42 s per layer after the first, 3.17 GB/s (the disk's own rate); the stand-in computed 6% of the time. With the layers' trunk files included, layers 1 to 12, O_DIRECT: 4.36 s per layer, 3.09 GB/s. So the page cache cost about half the rate in this pattern (a second copy and eviction, my reading, not measured separately), and the real path should read with O_DIRECT.
- **Pinning RAM:** 12 pinned slots of 15.72 GB (189 GB) took 187.5 s to allocate, about 1 GB/s. A resident RAM cache of experts is a one-time cost of minutes per 100 GB, so it is built once and kept, not per run.
- **RAM to cards only** (the 12 layers kept in the pinned slots by the first pass; the second pass reads nothing from disk): the first eight layers, one per card, were all on their cards after 6.3 s (126 GB at about 20 GB/s, as in step 1); all 12 layers by 12.1 s, 0.53 s per layer after the first; the stand-in computed 47% of the time. So even with every layer in RAM a card waits for its next layer about as long as it computes (one layer for one card takes 2.0 s, and eight cards loading at once about 0.8 s each).

### Step 3: what can rotate and what cannot (arithmetic on the measured figures, not a run of the model)

Per pass of one window through all layers the data is: experts 92 x 15.72 GB = 1,446 GB (1,347 GiB); trunk 56.5 GB (0.44 GB for an MLA layer, 0.65 GB for a KDA layer, 0.73 GB more for layer 0).
- **Trunk: can rotate, nearly free.** 56.5 GB fits in RAM beside everything else; a layer's trunk to its card is 0.6 GB, about 0.08 s at one card's 8 GB/s, 4% of the bytes of that layer's experts. It can be put on the card just before its layer, in the gap, and freed after; the cycle test with the trunk included showed no change in the rate.
- **Experts: can rotate, but the rotation is bounded by the disk.** From disk a layer takes 4.4 s (3.1 GB/s); from RAM about 0.5 to 0.95 s with the cards fed together; a layer's compute for 1000 tokens is about 0.25 s. RAM can hold about 330 GiB of pinned layers minus the trunk's 53 GiB, so about 18 to 22 layers of experts; the cards cannot hold more than the 8 layers in flight (one 14.64 GiB buffer per card, 6.6 GiB spare each). The other 70 or so layers must come from the single disk on every pass: 70 x 4.4 s + 22 x 0.7 s is about 320 s for a pass, against about 23 s of compute: the cards would compute for about 7% of that time.
- **Cannot:** keep every layer's experts in fast memory. 1,347 GiB of experts against 376 GiB of RAM and 188 GiB of card memory: about 42% at most, and only if nothing else were there.
- **What it takes for the cards not to wait:** compute per layer load must be about as long as the supply of that layer. For disk-fed layers (4.4 s) that is about 17 windows of 1000 tokens through each layer while its experts are on the card, so the layer's experts are read once and used by many tokens: run the layers in order with the whole prompt in chunks through each layer (the chunk's state kept per layer), instead of one window through all layers. For a prompt of about 16,000 tokens that would be a pass of about 320 s supply against about 380 s of compute, the cards nearly always busy; a single 1000-token window cannot be made to keep the cards busy by any rotation, because the data per layer is 60 times the compute per layer. Not yet measured: the chunked run, the long-prompt state (KDA state per layer is 6.3 MB; MLA keys and values for 16,000 tokens are about 1.6 GB per MLA layer while that layer runs), and the speed of that on the cards.
- **Hybrid (trunk on the CPU out of RAM, experts on the cards), for step 4:** the trunk work of a layer on the CPU engine is about 2 s for 1000 tokens (layer 0, the dense layer with only the trunk, took 1.9 to 2.6 s on 16 threads; the engine runs 16 threads, the machine has 96), against 0.17 s on a card. The CPU does the trunk in the time the disk is already taking per layer (4.4 s), so for the disk-bound case it costs the cards nothing; it only matters once the experts are RAM-resident or the windows are large. Step 4 needs the CPU's rate for the trunk part of a KDA and an MLA layer with more threads, which has not been measured.

## 2026-10-20 — is the disk used properly, and the RAM (the creator: "last machine gave 2 mirrors of 14 GB/s")

Read from the server (read-only; one setting changed and put back):
- **The drive:** one NVMe, `INTEL SSDPE2KX020T8` (the Intel DC P4510 2 TB class, a PCIe 3.1 x4 data-centre drive), on PCIe at 8.0 GT/s (generation 3), width x4, the maximum for the drive, attached to CPU node 1 (the cards hang off node 0). It is the only drive in the machine (`lsblk`); the root volume is LVM with ext4 on its one big partition. Block queue: scheduler none, 128 KiB largest request (`max_hw_sectors_kb` is 128, so the hardware does not allow larger; writing 1024 was refused).
- **Raw device against the volume:** O_DIRECT, one reader, 16 MiB blocks, 7.5 GiB: the raw device 2.7 GB/s, through LVM 2.7 GB/s, so LVM and ext4 cost nothing here; the file reads of step 1 (2.9 GB/s) agree. Four readers at the same time on the raw device: 4 x about 0.806 = 3.22 GB/s in all. The cycle test with two reader threads reached 3.17 GB/s. So the drive gives about 3.2 GB/s at a queue depth of a few requests and no more; our programs already read at that rate when they use O_DIRECT. The vendor's figure for this model as I remember it is about 3.2 GB/s sequential read; I could not look it up (the web search was blocked by a challenge), so that figure is unverified, the measurement above stands without it.
- **Why the CPU workstation was four times faster:** it had two NVMe drives mirrored (14.4 GB/s read with the same probe, about 7 GB/s a drive, so generation 4 drives); this rented server has one generation 3 drive. The disk is not being misused; it is a slower drive, alone.
- **RAM:** 12 modules of 32 GB DDR4 at 2933 MT/s, one module per channel, six channels per CPU. Theoretical peak about 141 GB/s per CPU; measured copy 51 GB/s per node with 16 threads, which is about 102 GB/s of memory traffic (read plus write), about 72% of peak, a normal figure. RAM is not being used badly either. The slow RAM thing in these tests was pinning (about 1 GB/s to lock pages), which is the driver's page-locking, not bandwidth.

## 2026-10-20 — network sources for the experts (the creator: use the other server through a tunnel)

Checked before building anything, because a tunnel cannot be faster than the link under it:
- **The other server (k3, the workstation with the two mirrored NVMe drives):** its only network port, `enp6s0`, reports 1000 Mbit/s (sysfs), so at most about 0.12 GB/s whatever the tunnel does, against 3.2 GB/s from this server's own drive: at best 4% more. Its disk (14 GB/s) would not be the limit; its port is. Not built: no key was put on k3 and no tunnel made, since it cannot pay for itself (a key on k3 would also widen access to a machine that holds the live data and cannot be justified for 4%). The link speed is the port's reported speed, not an end-to-end transfer test.
- **This server's ports:** three of its four 10 Gbit ports are up (`eno1np0`, `enp134s0f0`, `enp134s0f1`; the default route leaves by `enp134s0f1`), so the box itself could take about 1.2 GB/s per port.
- **Hugging Face as a source** (the dataset is public; ranges of 256 MiB of one experts file, no disk writes, one run each): 4 parallel requests 0.22 GB/s, 8 requests 0.31 GB/s, 16 requests 0.32 GB/s, 32 requests 0.35 GB/s. It stops at about 0.35 GB/s however many requests, the same rate the dataset download got (0.34 to 0.54 GB/s average), so it is the server side's rate, not this box's ports.
- **What it adds up to:** the drive 3.2 GB/s plus Hugging Face 0.35 plus k3 0.12 is about 3.7 GB/s, 15% above the drive alone, at the cost of two more sources to manage and a dependence on the network being there. The disk-bound time of a pass would go from about 320 s to about 280 s. Not enough to change the shape of the problem (the cards still wait for the data); not built.

## 2026-10-20 — all three sources together (local drive, Hugging Face, the other server)

Direction (the creator): use the local drive, Hugging Face and the other server (the Hetzner box, 128 GB RAM) together, the trunk read from the drive, and if that does not help, process more tokens so that the I/O matches the compute. "Hugging Face is a public cloud, it can serve several channels."

Built and measured (`probes/multi-read.cpp`: files read into RAM as one queue of 64 MiB chunks handed to whichever worker is free: O_DIRECT workers for the drive, `curl` range requests for Hugging Face, a forced-command ssh stream for the other server; the chunks that came over the network were compared with the local files, 0 differences in every run). For the other server a key was made on the GPU server and authorised on k3 for reading dataset files only (from the GPU server's address, no shell, one script that accepts only `read PATH OFFSET LENGTH` with a path checked against `expert-N/` or `trunk-N/`, the paths and numbers refused otherwise: tested). It has since been removed again from k3 (key line and script) and from the GPU server, as it did not pay for itself.

- **The drive alone**, four O_DIRECT workers, 64 MiB chunks: 3.15 to 3.17 GB/s into RAM (one file, 14,994 MiB: 4.96 s; four files, 62.9 GB: 19.96 s). That is the drive's rate again; chunk size is not the limit.
- **Hugging Face:** 0.34 GB/s with the tool's default settings and 0.33 GB/s with its documented high-performance mode (`HF_XET_HIGH_PERFORMANCE=1`) for a whole 15.7 GB file into RAM; 0.22 to 0.35 GB/s with 4 to 32 parallel range requests. More connections do not raise it. The tool itself says unauthenticated requests get lower rate limits; the supported way to a higher limit is a token of the creator's own account, which has not been tried (the token would have to be put on the server by the creator, not by me). Making more identities or addresses to multiply the limit was not done and would not be right.
- **The other server:** its port is 1 Gbit/s. One ssh stream 0.059 GB/s, four streams 0.113 GB/s (the port's limit). Its RAM does not matter: the port is the limit.
- **Drive plus Hugging Face, 24 range workers, four files (62.9 GB):** by the moment the drive finished (17.8 s) the drive had delivered 56.96 GB (3.20 GB/s) and Hugging Face 4.31 GB (0.24 GB/s): 3.44 GB/s together, 9% above the drive alone. The whole run took 20.5 s, not less than the drive alone (19.96 s): the network chunks still in flight when the drive was done held the end up. Over a long stream that end effect is paid once; inside a pipeline the network workers can fetch chunks for later layers while the drive finishes the current one, so the 9% would be real there, not here.
- **All three, 4 files:** Hugging Face 4.56 GB by the time the drive finished, the other server 0 GB: its four chunks (0.27 GB) arrived after the drive was done, so the whole run took 32.1 s (1.96 GB/s). With the Hugging Face workers running the ssh streams get almost nothing; both leave through the same uplink of this server, which suggests an overall internet limit for the box near 0.3 GB/s, but that is an inference from these runs, not something I measured on its own.
- **What it adds up to:** at best the drive plus about 0.25 GB/s: +8% sustained, from Hugging Face only; the other server adds nothing once Hugging Face is running. Not worth putting into the data path now; it can be added later as a prefetch of later layers.

On the trunk: it is 0.44 to 0.65 GB per layer, 3% or less of a layer's experts, so it can be read from the drive directly with the same O_DIRECT workers as the experts (the cycle test with the trunk included showed no change); it is not a separate problem.

Where this leaves the plan: the supply of experts to the cards is the drive's 3.15 GB/s, plus at most 8% from the network. A layer's experts take about 5 s to arrive; the layer's compute for 1000 tokens is about 0.25 s. The remaining way to make the I/O equal the compute is the one the creator named: more tokens per layer load.
