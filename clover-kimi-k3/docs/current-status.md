# Current Status - 2026-10-17

## Three distinct mechanisms

1. Expert-weight caching reduces disk reads by keeping reused expert weights resident.
2. Expert-result caching avoids repeated expert computation when the same request is seen again.
3. Prefix caching skips prompt prefill by restoring saved per-layer state and KV for cached prefix positions.

These mechanisms are separate and should not be combined into one claimed speedup.

## Recorded measurements (Ryzen 9 7950X3D host)

- Repeated request with expert-result cache: 3.27x speedup (A/B/A replay pattern), with matching output token IDs in the recorded run.
- Prefix cache loading 192 positions: 3.15x speedup (save 390 s, load 124 s), with matching output token IDs in that recorded test.

## Layer 1 with the 4-row x 4-token projection kernel (2026-10-17, k3 host)

`one-layer/layer-batch.c` now uses the same AVX-512 kernel as layer 0 (`input-to-layer0/VERDICT.md`) for the trunk matrices; switch `LB_WIDE=0/1` in `batch-run.sh`. 1,000 real tokens, window 1,000, 16 threads, experts locked in RAM, one run per setting; each run also ran the pod one token at a time (21.71 and 21.83 ms/token).
- Old kernel 4.307 ms/token (5.04x the pod); new kernel 3.427 ms/token (6.37x the pod), 1.26x. Output bit-identical to the pod for all 1,000 tokens in both runs, and the 15 stages compared on the first 8 tokens identical.
- Trunk matrices, the 13 matrices summed from the per-matrix table: 1.560 ms before, 0.684 ms after (Q/K/V 0.658 to 0.285, gate 0.217 to 0.094, attention output 0.259 to 0.101, shared expert gate/up 0.208 to 0.095); they now run at 870-960 GMAC/s. (An earlier line here said 1.68 to about 0.80; that figure included small non-matrix stages. The drop of 0.88 ms matches the total, 4.307 to 3.427.)
- The experts did not change: 2.624 ms against 2.626 ms, 201 GMAC/s, and are now 76.6% of the layer. Router scoring 0.045 ms at 144 GMAC/s.
- Why the experts run at 201 GMAC/s (`one-layer/expert-kernel-bench.c`, `expert-kernel-run.sh`; real expert data, layer 1, one run per setting, 6 repeats taking the best). The expert arithmetic is double precision, multiply then a separate add (no fused multiply-add). Raw peak of that on this host: 41 GMAC/s per thread, 566 GMAC/s (256-bit) to 638 (512-bit) on 16 threads, so the experts reach about 35% of their own peak (shipped kernel, 4 tokens per pass: 14.3 GMAC/s per thread resident, 219-224 on 16 threads for two matrices).
  - 512-bit versions taking 1, 2, 4 or 8 weight rows and 1 to 8 tokens per pass, 13 variants in all, were bit-identical to the shipped kernel and no faster in a useful way: best single thread 16.3 GMAC/s (2 rows x 4 tokens, +14%), 16 threads 213-228 against 219-224 (within noise). Wider registers and more rows per pass do not help the experts.
  - Cost split, one thread, matrix 0, per 16-column step of one row: table decode alone 1.83 ns; multiply-adds alone 0.85 ns per token (0.66 ns for one token); shipped kernel at 4 tokens 4.36 ns (decode and multiply-adds overlap by about 0.8 ns).
  - The multiply-adds are limited by re-reading the activations from L2: with 4 tokens, the multiply-add-only kernel takes 0.57 / 0.56 ns per token-step when the activations are 16 KB / 32 KB (fit in L1) and 0.85 / 0.84 when they are 64 KB / 115 KB. The shipped kernel walks all 3,584 columns of 4 tokens (115 KB, doubles) for every weight row.
  - Candidate (not built): tile the columns so the activations of a group of tokens stay in L1, keep each row's partial sums in memory between tiles (same additions in the same order), and decode each weight tile once for all the tokens that picked the expert instead of once per 4 tokens. Estimate only: 0.56 ns per token-step for the multiply-adds plus decode shared across 8-16 tokens would be 1.6x or more on the expert stage; not measured.
- Expert kernel attempts after that diagnosis (same bench, real expert data, all outputs bit-identical to the shipped kernel, single thread resident / 16 threads on 16 experts, matrix 0 and matrix 2 behaved alike): the shipped kernel costs 1.11 ns per token-step (14.4 GMAC/s per thread, 221 GMAC/s on 16 threads). (1) Column-tiled kernel with each weight tile decoded once into a buffer and applied to 4-32 tokens (512-bit): 1.09-1.35 ns per token-step single thread, 110-209 GMAC/s on 16 threads, no gain even at 32 tokens. (2) Column tiles with the shipped inline decode, loops token group > row block > tile > row, so the 4 tokens' activation tile (16 KB) stays in L1: 1.08 ns at 512-column tiles, 1.14 at 256 and 1,024; 195-199 GMAC/s on 16 threads, no gain. (3) Decode variants, one thread, matrix 0, per 16-column step: shipped 1.85 ns, one 512-bit gather 4.9 ns, code bytes split with shifts 1.94 ns, all steps using one table (no table cache misses) 1.51 ns; there are 465 pair tables of 2 KB (1.0 MB), so table misses cost about 0.34 ns of the 1.85. (4) 32 threads on the 16 cores' SMT siblings: 215 GMAC/s against 222 on 16 threads, no gain.
  - So the L2-activation explanation was only part of it: with the activations in L1 the full kernel did not speed up. Every arrangement lands near 1.1 ns per token-step; the shared limit is probably the load throughput (about 32 loads per 16-column step at 4 tokens, roughly 2 per cycle observed in the decode-only and multiply-add-only kernels), which I inferred from the counts and did not measure with a profiler.
  - Best bit-identical gain found: 512-bit, 2 weight rows x 4 tokens per pass, 16.2 GMAC/s per thread against 13.1-14.4 for the shipped kernel (+14%) and 240-244 GMAC/s on 16 or 32 threads against 216-222 (about +8-10%), single runs; not put into `layer-batch.c` (inside the layer, isolated gains were smaller than predicted before).

- Does the order of adding matter? Same 12,288 x 7,168 Q multiplications, token id 17374: adding each output's terms as one running total, column by column (the "multiply x_j into the whole column" order), gave a different last-bit result from the server's 16-lane order in 11,938 of 12,288 outputs (multiply then add) and 11,955 (fused multiply-add); worst relative difference 4.8e-3 and 5.5e-3 (I recorded the count and the worst, not the typical size). One token, one matrix. The model's reference arithmetic is the 16-lane order, so a column-order kernel would not be bit-identical to it. Size of the gap, against the exact answer in double precision (outputs have typical size 0.97): the server's 16-lane float order has RMS error 1.6e-07 (largest 1.3e-06); the column-by-column float order has RMS error 1.2e-06 (largest 1.3e-05); the two float orders differ by at most 1.3e-05, i.e. about 1e-5 of the typical output. So both approximate the same exact number and the 16-lane order is the more accurate of the two here (one token, one matrix). Whether a difference of that size changes discrete choices (expert routing, the next token) over 93 layers has not been tested. Rounding once at the end (adding in double precision, then converting to float): RMS error 2.5e-08, largest 3.7e-07, about 6.7x more accurate than the server's order, but 10,626 of 12,288 results differ from the server's float result, so it is more exact and not the same bits as the original arithmetic, which rounds after every addition. Double accumulation halves the multiply-adds per vector instruction (4 doubles against 8 floats in 256 bits); that cost is an expectation, not measured.
- One complete 7,168-term dot product, step by step (`projection-show.c`, beta row 0, token 17374): 448 blocks of 16 columns; each of 16 lanes keeps its own total over 448 products; after the last block the lane totals are folded 16 -> 8 -> 4 -> 1 by fixed additions (865.938354) and multiplied by the row scale 0.00322957686 to give 2.79661441, bit-identical to the server's kernel; cost 7,168 fused multiply-adds, 15 additions, 1 multiply, 7,168 weight bytes read. - Speed of column order against the 16-lane row order (`proj-bench.c`, same machine, real matrix shapes, 32-token tile, 16 threads, best of 5, AVX-512, 64 rows x 4 tokens per pass, weights repacked for column order; isolation numbers, one session): 12,288 x 7,168: column 885 GMAC/s, row 4x4 1,053; 4,096 x 7,168: 1,133 against 1,069; 4,096 x 1,024: 1,138 against 996; 7,168 x 33,792: 814 against 970. ## DSpark width chosen per pass, and DSpark with the 4-bit trunk (2026-10-18)

- Why: a fixed 8-wide pass made prose 1.5x slower than plain (see above). `best_draft_width` in `whole-model.c` picks, per pass, the width (0 to 8 draft tokens) with the most expected tokens per plain-step time. Cost model: one more position costs 0.31 of a plain step (measured 1, 2, 4, 8 positions: 3.33, 4.57, 6.69, 10.65 s, exact trunk). Chance a draft token is right: draft tokens right / tried, decayed by 0.9 per pass, starting at 0.7; with no draft verified, the first guess is still compared with the token the model made. The draft model costs 0.165-0.26 s per pass (2.3-5.0 s for 48 tokens).
- `scripts/check-dspark-drafter.sh 48 "0 1"`, one run per prompt and trunk, ids identical to plain decoding in all 6 comparisons (the 4-bit comparison is against 4-bit plain decoding, not against exact):
