# loader - can the differential driver fail? Mutation controls (independent verifier, 2026-10-25)

Question: can the differential driver of the `loader` crate (`verify/ld_driver.cpp`, C++ reference `ref/libloader_ref.so` against `target/release/libloader.so`) FAIL? It was run against deliberately broken copies of the Rust crate. I did not write the crate or the driver; neither was changed (the driver binary on the box is the recorded one, md5 `f104b44a3bd82b6657e6e68f4bdb5fa6`; `ref/libloader_ref.so` md5 `bb41075c183f95a9d9d800a0a377477b`).

## Method

- Mutant = copy of the crate in `~/rustmig/loader/verify/work/mut/<name>/` (Cargo.toml, Cargo.lock, src/, include/), exactly one logical change in `src/*.rs` (a few mutants need two hunks of one file to express one bug; the description says so), built with `export PATH=$HOME/.cargo/bin:$PATH; cargo build --release` (cargo/rustc 1.95.0 on the box today). The diff of each is `<name>.diff` here (first line = description). `M00` = unmodified copy (control). The box sources are byte-identical to the Windows tree (raw md5 compared, CRLF in both).
- Run: `run_mut.sh` = the matrix of `verify/run.sh 200` (2820 units: barrier/wait/stress/race/init2 200 each, fifo 1000, open 600, shm 100, real/fatal/natural 40 each) against the reference and against the mutant's `.so` (`mut_unit.sh` is `verify/unit.sh` with the library path as a parameter), one mutant at a time, all under `nice -n 10`, at most 20 units at a time, each process under `timeout 60` and a 2.5 GB address-space limit. A unit is **FAIL** when the mutant's run does not print `RESULT ... PASS` / exits non-zero / its canonical `C ` lines differ from the reference's; **REFBAD** (reference failed) never occurred.
- **CAUGHT = at least one FAIL unit.** Counts are the `UNIT ... FAIL` lines of `units.log` (`analyze.py`; every run has exactly one line per started unit, no duplicates). Raw per-unit files were deleted after each run; kept during the campaign: `units.log`, `summary.txt`, `jobs.txt`, and the driver output (`*.fail.txt`, first 30 KB) of every failing unit. **These were deleted by mistake at the very end, see "Mistake of mine" below; `analysis.txt` was generated from them before.**
- Partial runs: a mutant that hangs most units would cost hours (each hung unit waits 20 s in the driver's own timeout), so from M08 on the runner stops starting new units once 100 units of the run have failed (`MAXFAIL=100`; up to 20 more are already in flight). Such a run reports `units run < 2820`; the verdict CAUGHT does not depend on it. Every mutant that was not caught ran all 2820 units. (M00-M07 ran before this option existed and ran in full.)
- Racy / ordering mutants were run 3 times (tags r1, r2, r3) and the number of runs that caught them is reported. Not-caught mutants additionally ran a soak at N=1000 (14100 units), `cargo test --release` of the mutant, and probes (below).
- Ordering mutants: the crate has **no atomics** in `src/` (`grep Ordering\|Atomic src/*.rs` only matches `tests.rs`); everything is published through `Mutex`/`Condvar`. There is no `Release`/`Acquire` flag to weaken, so that class of the brief does not exist for this crate; the nearest mutants are the counter / notify / lock-scope ones, and x86 would hide weak-memory effects anyway.

## Environment

Box `gpu`, Ubuntu 24.04, kernel 6.8.0-147, x86_64, 96 cores, load average 40-75 during the runs (other agents' work plus my 20 units). No GPU, no CUDA, no sudo. Disk: see the end.

## Result in one paragraph

101 mutants (99 numbered + the two widened-window twins M05w, M11w) plus the control M00. The driver **fails on 86 of the 101**; 15 pass in every run (2820 units at r1, 3 runs for the racy ones, 14100 units in the soak). Of those 15: **5 equivalent** (M06, M17, M50, and M75, M76 whose `.so` is byte-identical to M00), **2 not observable in the range the driver uses** (M58, M59: 32-bit multiplications, the value never differs), **1 caught by `cargo test` only** (M51, fd 0), **1 contract-silent** (M84: the Rust job uses the card captured at the call, the original reads `h->card` live), and **6 real gaps of the driver**: M05 (pending++ after the push, race window of nanoseconds), M27 (thread stack 2 MB instead of 8 MB), M82/M83 (handle bookkeeping written after the job is queued), M87 and M92 (guard order for requests the driver never generates). The control M00 passes 2820 of 2820 (r1) and 14100 of 14100 (soak). By class (caught / total): concurrency 25/29, job order and callback arguments 11/11, open / path / exit text 15/17, prefill and pread 14/16, bounds / bookkeeping / guards 21/28.

Unit lines over all runs: 500,567, no duplicate unit line in any run, the reference never failed (REFBAD 0).

## Driver weaknesses and proposed fixes (not applied)

1. **Bookkeeping order and live reads (M82, M83, M84).** The callbacks never look at `*h_L`, `*h_card`, `*h_k_in` or `handles[layer]`. Fix, tested as a patched copy (`mk_driver_bk.py` -> `probe/ld_driver_bk.cpp`): (a) in `cb_trunk` (first callback that gets the handle) check that `*h_L`, `*h_k_in`, `*h_card` and `g_handles[layer]` are already written; (b) in the `open` scenario with `hold=1`, overwrite every handle's `*h_card` after all `ld_open_layer` calls returned and restore it after `ld_wait` (only if the header is changed to say the job uses the captured card; today it is silent and the original reads it live). Result above: M83 204/400, M84 196/400, control 0/400, M82 0/400.
2. **No test for "a waiter asleep when the counter reaches 0 must wake" under hot job streams (M05, M14, weak M11).** The driver's wait checks (c)-(f) rely on gated jobs. `lw_probe.c` (here) is a ready scenario: several threads call `ld_wait` in a loop while the main thread submits single jobs and hot bursts of 2-8 tiny jobs to one card; every 25 rounds the stream stops and every waiter must still be spinning (a stuck waiter has slept through its wake-up). It sees M11, M14, M15, M05w, M11w in 3 of 3 runs and M05 in 1 of 3 instrumented runs. Porting it into `ld_driver.cpp` as scenario `hotwait` would also raise the catch rate of M14 from 0.04-0.18 % of units.
3. **Opens are not events (M33).** Let the `open` interposer append an `open` event to the card's event log (the card is known from the layer of the path), so the order `state` / `open` is checked in every `open` unit, not only on the fatal path.
4. **Only EINVAL is used to refuse `O_DIRECT` (M46).** Add refusal modes with other errnos (EACCES, EOPNOTSUPP, ENOENT-then-success) in `open`: the header says "any failure of the first open, whatever errno".
5. **Guard order combinations (M87, M92).** Add `fatal` cases: a request wrong in both ways (card 9, layer 93, prefill) expecting the card message (header: card check first); `ld_init(NULL)` after a valid init (needs a header decision first).
6. **Stack depth (M27).** Either state the stack size in the header and add a job that touches e.g. 4 MB (`lw_probe stack` shows the shape), or record in the header that it is unspecified.
7. **Large `expert_raw` (M58, M59).** The driver caps at 17547264. A unit test with the crate's fake libc and fake `host_alloc` could pass `expert_raw = 1<<31` without allocating (offsets and lengths of the `pread` calls are what is asserted); not done here.
8. fd 0 (M51) cannot be produced by the driver; the unit test covers it (keep it).

## What the run does not cover

- 101 hand-made single changes are a sample, not a mutation score of the crate; equivalence of M06, M17, M50 is argued from the header and the original text, proven only for M75 and M76 (identical machine code). M58/M59 are equivalent for `expert_raw < 2^30` only.
- Timing-dependent catch rates (M11, M14, M25) are those of this box on this evening (load 40-75, 96 cores, kernel 6.8.0-147, x86_64); they will differ elsewhere. x86 hides weak-memory bugs; the crate has no atomics, so the Release/Acquire class of the brief does not exist here.
- Partial runs (MAXFAIL=100) for the mutants that hang or fail most units: all of them already failed in their first 100-300 units; their per-scenario columns are incomplete by construction.
- Units killed by `timeout 60` count as FAIL (e.g. M24: `rc=124`); I did not separate "driver detected a hang" (its own 20 s timeout) from "killed by my timeout" in the table; the first-failure column shows which.
- Not exercised by any mutant: `close` of the fd (the crate has none), `expert_raw = 0` or not a multiple of 512 under a real `O_DIRECT`, thread-creation failure, a failing `write` to stderr, aarch64.
- GPU, CUDA, engine: not touched (rules).

## Mistake of mine, and what it cost

The cleanup script archived the per-run `units.log` files with `tar -c --wildcards '*/units.log'`, which does not glob in create mode ("Cannot stat"); the script went on and deleted `out/`, so **the raw `units.log` / `summary.txt` of the 102 + 19 + 19 + 16 + 9 runs on the box are gone** (`mutants/units-logs.tar.gz` on the box holds only `progress.txt`). What remains: `analysis.txt` (generated by `analyze.py` from those files before they were deleted: counts per scenario, first failure line of every run), `logs/progress.txt` (one line per run with PASS / FAIL counts and wall time), the probe and cargo-test outputs, the diffs, the md5 lists. The campaign is repeatable: `mk_mutants.py` rebuilds every `.so` (the md5 list shows whether a rebuild is byte-identical) and `run_mut.sh` reruns a mutant in about 30 s to 6 minutes. Lesson written to memory: test an archive before deleting what it was made from.
