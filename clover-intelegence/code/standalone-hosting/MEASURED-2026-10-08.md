# Standalone hosting — measured, 2026-10-08

Host `k3` (AX102): Ryzen 9 7950X3D, 16 cores used of 32, 124 GB RAM,
`/dev/md2` raid1 of two KIOXIA KCD8XRUG1T92 on PCIe 4.0 x4.
Prompt unless stated: `The capital of France is` = `1008 10484 318 15383 387`, 1 output token.
Every arm re-run; caches dropped before cold arms. Tokens checked on every arm.

## Per request, France, resident process

**Corrected 2026-10-08 (second pass).** The figures below were first recorded with
`CLOVER_HARDMAX_LAYERS=999`. That setting makes 100% of expert reads cacheable and leaves the
first output token unchanged, but it **degrades generation from the second token onward** --
see "hardmax" below. The supported configuration keeps hardmax at its default of 46.

| configuration | single output token | note |
|---|---:|---|
| buffered reads, serialised | 21.67 s | starting point |
| + `K3_EXPERT_DIRECT=1` | 15.54 s | O_DIRECT |
| + pipelined reader | 11.07 s | dedicated pthreads |
| + direct int8 decode, thread binding | ~9.7 s | general path, any prompt |
| + stored expert results, hardmax 46 | **5.97 s** | france/japan prompt pass only |
| ~~+ stored results, hardmax off~~ | ~~1.63 s~~ | **withdrawn: breaks generation** |

The 1.63 s figure required three conditions that do not hold together (single token,
hardmax off, fully cached). It is not achievable without the quality regression.

## Prompt pass and output-token generation

Six prompts, six output tokens each, `K3_RESULT_SET=france`, hardmax at its default.
All seconds.

| prompt | in | prompt pass | each output token | total | readGB | hits |
|---|---:|---:|---:|---:|---:|---:|
| France | 5 | 5.97 | ~3.67 | 24.30 | 179.9 | 3600 |
| Japan | 5 | 7.39 | ~3.67 | 25.73 | 200.0 | 2160 |
| Italy | 5 | 7.39 | ~3.66 | 25.70 | 200.1 | 2160 |
| Planet | 4 | 7.47 | ~3.67 | 25.83 | 199.1 | 720 |
| Maths | 4 | 8.17 | ~3.65 | 26.44 | 208.6 | 0 |
| Sky | 6 | 9.30 | ~3.65 | 27.57 | 222.7 | 720 |

**Output-token generation is flat at ~3.66 s** regardless of prompt, input length or how much
of the prompt pass was cached, and it is ~75% of a six-token request. It is a full forward
pass over all 93 layers, not a lookup:

```
step           total  readGB  stall      Q      X   rest  unacc   hits  Qcalls
prompt pass(5)  5.97    50.7   1.38   1.39   2.34   0.28   0.59   3600    1159
output token 1  3.68    25.8   0.92   1.37   0.93   0.14   0.30      0    1159
output token 5  3.70    25.8   0.96   1.39   0.90   0.14   0.31      0    1159
```

Same 1,159 `Q` calls every step. Reads 25.8 GB of newly routed expert weights. `hits = 0`
because a generated token has no stored observation and cannot have one.

```
prompt pass, 5 positions : Q moved 53.83 GB -> 38.8 GB/s, 388.1 GFLOP/s, 9.99 FLOP/byte
output token, 1 position : Q moved 53.83 GB -> 39.2 GB/s,  78.4 GFLOP/s, 2.00 FLOP/byte
```

Identical weight traffic, both at ~39 GB/s. Only the useful work differs: 10 FLOP/byte when
five positions share the read, 2 FLOP/byte for one. **Batching concurrent requests is the only
remaining lever** -- `NPOS_SLOTS=8` already allows `T` up to 8; what is missing is a scheduler.

An arbitrary prompt with no stored observations takes **~9.7 s** for the prompt pass.

## Hardware ceiling

`fio` 13.51 GB/s at 8 readers. Per-drive PCIe 4.0 x4 is ~7.4 GB/s, so the pair caps near 14 GB/s.
Per-device counters during one request: nvme0n1 88.93 GB / nvme1n1 89.23 GB = 49.9/50.1 split,
so md balances across both members.

| expert read path | rate |
|---|---:|
| buffered `pread` | 6.04 GB/s |
| O_DIRECT, batched | 11.25 GB/s |
| O_DIRECT, pipelined | 12.41 GB/s |

Read concurrency knee is 16; 32/48/64 are all slower.

## Stored expert observations

`root-N/observations/{france,japan}/` hold gate/up/activation/down, 80 records per layer,
933 MB total, against 1.44 TB of `experts.direct`. 92 x 80 = 7,360 = one record per expert stage.

Matching on expert id **and** bit-exact input, over 7,360 steps:

| | |
|---|---:|
| record found by expert id | 7171 (97.4%) |
| live input bit-exact | 7360 (100%) with hardmax off |
| worst `down` difference when input matches | **0** |
| worst `down` difference when only id matches | 2.20627 |

Matching on id alone is unsafe; the exact-input check is what makes this memoisation
rather than replay. Verified both ways: computing all 7,360 experts from 99.72 GB of
weights and looking all 7,360 up from 933 MB both yield token 17374.

### hardmax: do not disable it

`CLOVER_HARDMAX_LAYERS` defaults to `46`. Disabling it makes the engine match the captured
reference on all 92 layers and takes stored coverage from 49% to 100%. It also **ruins
generation**, which the capture cannot detect because it only ever covered the five prompt
positions:

| configuration | France, 5 output tokens |
|---|---|
| `snapfold` + `snapshot`, hardmax 46 (default) | ` Paris. The Eiffel` |
| pure defaults | ` Paris, and the capital` |
| hardmax 999 + `snapfold` + `snapshot` | ` Paris.",\n+            "` |
| hardmax 999 alone | ` the county of Ville` -- first token wrong |

Matching the reference bit-exactly and generating good text are different properties.
Validating only the first token cannot distinguish them.

Supported configuration:

```sh
CLOVER_SNAPFOLD=score CLOVER_SNAPSHOT=layer     # hardmax left at its default of 46
```

With hardmax at 46 the stored values are valid for layers 1-45 only, so France gets
45 x 16 x 5 = 3,600 hits and Japan 45 x 16 x 3 = 2,160. The prefix arithmetic below still
holds, over 45 layers instead of 92.

All six prompts generate correctly at this setting:

```
France  -> " Paris. The Eiffel Tower"        Planet -> " Jupiter, followed by Saturn,"
Japan   -> " Tokyo. Tokyo is the largest"    Maths  -> " four. I put sugar in"
Italy   -> " Rome. It is a city"             Sky    -> " blue because of the scattering of"
```

### per-layer divergence under hardmax

```
L1..L45   80/80/80   bit-exact
L46       80/64/0    hardmax fires
L47..L92  80/~76/0   never matches again
```

With the %12 snapfold rule on instead, divergence starts at layer 12 (880 = 11 x 80 matches).
Setting the variable empty does **not** disable it; `CLOVER_HARDMAX_LAYERS=999` does.

### the observations behave as a prefix cache

Six prompts run with only **france** loaded. Hits are exactly `92 x 16 x shared prefix positions`:

| prompt | shared positions | hits | readGB | token |
|---|---:|---:|---:|---|
| France | 5 | 7360 | 0.00 | 17374 |
| Japan | 3 | 4416 | 41.66 | 40484 |
| Italy | 3 | 4416 | 42.31 | 31082 |
| Planet | 1 | 1472 | 59.08 | 75591 |
| Maths | 0 | 0 | 79.40 | 4771 |
| Sky | 1 | 1472 | 83.05 | 9447 |

All six correct. No cross-contamination: causal attention means an unchanged prefix has a
bit-identical residual, so those records are genuinely the right answer.

## Q is memory bound

| | achieved | ceiling |
|---|---:|---:|
| compute | 416.7 GFLOP/s | ~2150 GFLOP/s |
| weight bandwidth | **41.7 GB/s** | ~47 GB/s |

53.83 GB of weights per request, arithmetic intensity 10 FLOP/byte (= 2 x 5 positions),
so batching is already optimal. Floor is 53.83/47 = 1.15 s against 1.29 s achieved.
Q cannot improve further without reading fewer bytes.

The qkv palette is `palette[c] == (float)(int8_t)c` on all 68 KDA layers, so the
`_mm256_i32gather_ps` reproduced a sign-extend. Replacing it with `_mm256_cvtepi8_epi32`
is bit-identical: 1.542 s -> 1.291 s, 34.9 -> 41.7 GB/s. Checked at run time, not assumed,
because the 24 MLA layers (`layer % 4 == 3`, and 92) carry a different table.

`OMP_PROC_BIND=close OMP_PLACES=cores` is worth a further 13% on Q and was being dropped
by `env -i`.

## Rejected after measurement

| tried | result |
|---|---|
| `K3_RESIDENT_WARMUP=1` | costs 19.74 s, saves 3.1 s — it pre-touches the mmap one 4 KB page at a time, single threaded |
| trunk in `/dev/shm` | 29.3/24.7/22.8 s — starves the expert page cache, RAM 123 -> 70 GB |
| reader thread using OMP | expert bucket 4.3 -> 9.6 s; its team competes with the compute team |
| splitting expert reads into 2 MB units | no change buffered |
| strict `root_resident` (every page) | forces the copy path, destroys the warm case |
| pull concurrency 32/48/64 | 10.4–10.7 GB/s vs 11.25 at 16 |

## O_DIRECT is workload dependent

| | same prompt repeated | six different prompts |
|---|---:|---:|
| O_DIRECT on | 8.60 s | 15.54 s |
| O_DIRECT off | **3.33 s** | 21.67 s |

Repeated prompts reuse the page cache, so O_DIRECT loses. Varied prompts get no reuse —
six prompts need ~600 GB against ~48 GB of free page cache — so O_DIRECT wins. Default is on.

## Caveats

- n=1 to n=3 per arm. Run-to-run spread of ~1 s was seen across the session; the
  six-prompt benchmark repeated at 35.29 / 35.33 / 35.40 s, which is tighter.
- The pipelined reader is new concurrency code with six prompts behind it, not a proof.
- Stored expert results help the **prompt pass only**. They never help output-token
  generation, which is ~75% of a six-token request.
- Startup is ~9.5 s cold to load the 75.9 GB payload, paid once per process.
- The first version of this file reported 1.63 s and recommended disabling hardmax. Both
  were wrong: the figure came from a configuration that degrades generation, verified
  against a first-token-only check that structurally could not detect the failure.
